## 插曲一：训练比 Week2 慢 65% 的诊断（重要教训）

首轮启动后发现 17.2s/步，而 Week2 同配置只要 10.4s/步。诊断过程：

1. **排除配置差异**：Week3 与 Week2 的 loss 曲线逐点一致（seed 42 复现完美），
   说明慢的不是训练本身。
2. **看硬件状态**：GPU 利用率显示 98%，但功耗仅 333W/450W——"忙而不饱"，
   典型的计算被打断特征。
3. **查共享进程**：`nvidia-smi` 列出 Chrome、Edge WebView、微信、Steam、VS Code
   全挂在 4090 上——**桌面程序在和训练抢 GPU 时间片**（Windows WDDM 调度）。

关闭抢占程序后，基线自动恢复 10.12s/步。**教训：Windows 上训练前先清空 GPU
共享进程，否则白白慢近一倍。**

## 插曲二：吞吐基准测试（结论：基线配置已是最优）

为验证"能否更快"，对 4 种方案各跑 2000 条样本（等效 batch 恒为 16，
s/step 直接可比）：

| 方案 | s/步 | 峰值显存 | 结论 |
|---|---|---|---|
| bs1 + 梯度检查点（基线）★ | **10.12** | 13.3 GB | 最快且显存最省 |
| bs2 + 梯度检查点 | 10.38 | 18.1 GB | 无收益：packing 已把每步填满 2048 token |
| bs4 + 梯度检查点 | 12.00 | 23.9 GB | 更慢且近 OOM |
| bs1 关梯度检查点 | 12.00 | 23.8 GB | 重计算省了，但显存带宽成瓶颈，反而更慢 |

两点反直觉的发现值得记进周报：
1. **序列打包后，加大 micro-batch 无意义**——每步已是满负荷矩阵乘。
2. **关梯度检查点反而更慢**——3B 模型 + 2048 序列下，激活全存导致显存压力
   逼近上限，碎片化与分配开销吃掉了省下的重计算时间。

**真并行（两组同时训）不可行**：单组 13.3GB，24GB 卡塞不下两组 bf16 LoRA；
换 QLoRA 能塞下但改变了实验对象（4-bit 基座），对比结论会失效，不采用。

## 插曲三：加速内核调研与安装（备用于 Week4）

调研结论（详见 `docs/WSL2迁移评估.md` 与 FAQ Q3/Q4）：Windows 上可行的加速是
FlashAttention-2（社区预编译轮子，cu124/torch2.6/cp312 精确匹配）+ Liger Kernel
（依赖 triton-windows）。安装踩坑：liger-kernel 声明依赖 Linux 包名 `triton`，
需 `--no-deps` 绕过。三个包均已装入 `.venv` 并验证 import 通过。

本周 4 组实验统一使用 SDPA（同一口径，耗时/显存直接可比）；FA2/Liger 作为
已就绪的基础设施留给 Week4 DPO（训练量更大，收益更明显），启用方式：yaml 加
`flash_attn: fa2` 与 `enable_liger_kernel: true`。

## 实验结果

数据表见 `deliverables/实验结果汇总.md`（自动生成，含每组 loss/耗时/显存与
组内最优 ★ 标记）；假设验证与分析见周报第三节。

**阶段性结论（组A，前 2 组完成时记录）**：r32 全面优于 r8——train loss
1.3085→1.2590、eval loss 1.2788→1.2629，代价仅 +5% 耗时 / +0.5GB 显存 /
adapter 57→228MB。3 轮内未见过拟合迹象；train 降幅大于 eval 降幅，说明
部分新增容量只在拟合训练集。

**阶段性结论（组B，第 3 组完成时记录）**：lr2e-4 优于 1e-4——eval loss
1.2789→1.2656，且全程无震荡；零额外成本追平 r32 级别的收益，性价比最高。
两组信号叠加指向组合候选 r32 + lr2e-4（待组C 出结果后按计划表 §6 判定，
组合若未跑过需补跑验证）。原始日志随每组完成滚动归档至 `deliverables/logs/`。
