## 〇、本周的三个关键判断（先说结论）

写代码之前，任务书里有三处需要先定性，否则整周会做散：

### 1. `create_react_agent` 是个歧义名字，而 Day31 的交付要求替我们选好了

LangChain 生态里有两个同名函数，对模型的要求完全相反：

| 函数 | 机制 | 对模型的要求 |
|---|---|---|
| `langchain.agents.create_react_agent` | **文本版**：prompt 驱动 + 输出解析 | 只要会按格式写字 |
| `langgraph.prebuilt.create_react_agent` | tool-calling 版 | 必须支持 native `bind_tools` |

**Day31.1 要求构造 `Thought/Action/Action Input/Observation` 格式的训练数据**——那正是
文本版 ReAct 的格式，不是 tool-calling 的 JSON 格式。若 Day29 采用 tool-calling 版，
Day31 微调出来的格式与 Agent 期望的格式对不上，整周会断成两截。**故全周采用文本版。**

附带的工程原因：本地 HF 模型走 `bind_tools` 支持不稳；且 **LangChain 1.0（2025-10）
已经删除了 `langchain.agents.create_react_agent`**，v1 只保留基于 tool-calling 的
`create_agent`。因此本周把 langchain 钉在 `>=0.3.0,<1.0.0`（实装 0.3.30）。

### 2. 用 DPO 模型做 Agent，未必比 SFT 模型更好——这正是本周最值得测的对照

第 4 周的交付模型是拿**安全拒答**对齐出来的（β=0.5、约束紧、红线拒答率 100%）。
这种"对齐税"可能以两种方式伤害工具调用能力：对工具请求过度谨慎、输出风格被对齐
得偏离 ReAct 格式。因此 Day29 起就把 **base / week3-SFT / week4-DPO 三个 policy 做
并排对照**，而不是只跑 DPO 一个。这既延续了 Week3/Week4 一贯的控制变量方法论，
也直接为 Day32 的错误分析提供最有价值的素材。

### 3. Day28.3 的知识库必须"反向设计"

Day30.2 要求的多步任务是"查询 XX 产品的价格，加上运费后计算总价，判断是否超过预算
1000 元"。如果先随手造知识库、再去问这个问题，大概率卡在"知识库里没有这个产品"。
**做法反过来：先定死 Day30.2 的目标任务，再造能支撑它的数据。**

于是知识库里的商品被刻意设计成两类边界：

| 商品 | 价格 | 运费 | 总价 | vs 预算 1000 | 设计意图 |
|---|---|---|---|---|---|
| 星尘 X1 智能音箱 | 899 | 68 | **967** | 未超 | **临界但不超**，防止模型靠"感觉贵"猜对 |
| 追光 S3 显示器 | 1299 | 120 | **1419** | 超 | 单价已超预算，考察是否仍老实走完计算 |
| 云雀 Pro 无线耳机 | 459 | **0** | 459 | 未超 | 运费为 0，考察会不会凭空捏造运费 |

## 二、Day28：LangChain 环境与前两个工具

### 2.1 CalculatorTool —— 为什么是 AST 白名单而不是 `eval`

工具的输入直接来自 LLM 的 Action Input，那是**不可信输入**（模型可能被 prompt injection
诱导，也可能自己胡乱拼接）。`eval("__import__('os').system(...)")` 一行就能拿下宿主机。

这里**不做黑名单过滤**（黑名单永远漏，如 `().__class__.__bases__` 这类绕过），
而是走**白名单 AST**：先 `ast.parse` 成语法树，逐节点核对类型，只有字面量、
四则/乘方/比较运算与白名单数学函数可以求值。`__import__`、属性访问、下标、lambda、
推导式在**求值之前**就被拦下——不存在被执行的路径。

三层防护：

| 层 | 防什么 | 做法 |
|---|---|---|
| ① 节点白名单 | 代码注入、沙箱逃逸 | 只放行字面量/运算/白名单函数，其余抛异常 |
| ② 幂运算限幅 | `10**10**10` 内存炸弹 | 指数 ≤256、底数 ≤10¹⁵ |
| ③ 结果限幅 | 几十万位整数撑爆 context | 整数位数 ≤100 |

**输入归一化**：中文模型很爱输出全角字符（`８９９＋６８`）、千分位逗号、尾部等号、
引号包裹。这些不是"算错"，是格式噪声，在工具层磨平，但**把归一化前后的差异记录下来**
——Day32 要靠它区分「参数提取错误」和「单纯格式噪声」，两者的优化手段完全不同。

其中 `^ → **` 的转换值得单说：数学书写里 `^` 是乘方，但 Python 里是**异或**，
`2^10` 会静默算出 `8` 而不报错。这是最危险的一类错误——不报错的错误。

### 2.2 KnowledgeRetrievalTool —— 为什么不上向量检索

任务书要求"基于本地 JSON 文件的模拟知识库"。上 FAISS + embedding 模型会引入几百 MB
依赖，且在 6 商品 + 5 文档的规模上，稠密检索相对关键词检索没有任何优势，**反而引入
检索不确定性**：Day32 做错误归因时，如果检索层本身是黑盒，就分不清是"模型选错工具"
还是"工具召回错文档"。

故采用**确定性、可解释**的混合打分：

```
score = 4.0 × 关键词精确命中
      + 2.0 × 标题子串命中
      + 1.0 × 正文字符 bigram 重合度
      + 0.5 × 字段意图词命中（价格/运费/保修…）
```

中文没有空格，不引入 jieba（又一个依赖，且对"星尘X1"这类生造词表现不稳），
改用**字符 bigram** 求重合度——对中文短查询召回质量已足够，且完全确定性。

两个刻意的设计：

- **返回自然语言而非 JSON**：返回值会作为 Observation 拼进 prompt。3B 模型读 JSON 时
  容易把花括号引号当成要继续输出的格式，破坏 Thought/Action 结构。
- **未命中时明确说"没找到"并列出可用范围**：而不是勉强返回一个低分结果。这直接
  抑制了 Day32 的一类死循环——模型拿着同一个查询反复重试。

## 三、Day29：ReAct Agent 构建

### 3.1 最难的一处工程：让 chat 模型「续写自己」

文本版 ReAct 要求模型**接着已有的 Thought/Action/Observation 往下写**，但 Qwen 是 chat
模型——`apply_chat_template` 之后每个 assistant 轮都从空开始。

朴素做法是把 `agent_scratchpad` 塞进 user 轮。**实测这会直接导致死循环**：3B 模型
把它当成用户提供的资料，然后从头再输出一遍 Thought1，永远走不到第二步。

正确做法是 **assistant 前缀填充（prefill）**：

```python
text = tok.apply_chat_template(messages, add_generation_prompt=True)
text += assist_prefill        # ← scratchpad 拼在生成起点之后
```

模型看到的是"一个说到一半的自己"，自然会续写下一个 Thought。为此自定义了
`LocalQwenLLM(LLM)`，用 `<<<SYSTEM>>>/<<<USER>>>/<<<ASSISTANT>>>` 三个哨兵把
LangChain 的单串模板还原成 chat 三段式。

### 3.2 必须能在 `Observation:` 处停住

ReAct 的循环是：模型写到 Action Input → **框架真正调用工具** → 把结果作为 Observation
回填。如果模型不停，它会自己把 Observation 也编出来（幻觉工具结果），Agent 退化成
自问自答。

`HuggingFacePipeline` 对 stop 序列的支持依赖版本且不稳，故用 `StoppingCriteria` 精确
控制。**按解码后的字符串判停而非 token id**：`Observation` 在不同上下文会被切成不同的
token 组合（前导空格/换行都会改变切分），按 id 匹配漏判率很高。

### 3.3 三个防跑飞参数，同时也是 Day32 的观测口

| 参数 | 值 | 作用 |
|---|---|---|
| `max_iterations` | 6 | 3B 模型极易在"查不到→换说法再查"之间横跳 |
| `handle_parsing_errors` | True | 格式错时把错误作为 Observation 回灌，给一次自我纠正机会 |
| `early_stopping_method` | force | 撞上限时给出当前最佳答案而非抛异常 |
| `return_intermediate_steps` | True | 留档全部中间步骤，供 Day32 归因 |
| 解码 | 贪心 `do_sample=False` | 保证可复现，与 Week3/Week4 评测口径一致 |

**撞上限的次数就是「死循环」的统计口径**。

## 四、Day30：第三个工具与多步推理

### 4.1 CodeExecutorTool —— 名叫 Executor，但绝不 execute

任务书 30.1 明确要求"调用 Python AST 模块做语法检查，**非真正执行**"。

**工具名故意取 `code_check` 而不是 `code_executor`**：ReAct 里模型极大程度上按名字的
字面意思选工具，叫 executor 会诱导它拿来求运行结果，然后把"语法正确"误读成"运行
结果"。这个改名的收益在 Day32 用 A/B 对照验证。

`ast.parse` 只做**语法**分析。下面这段能通过检查：

```python
def f():
    return undefined_variable + 1
```

所以工具明确只承诺语法层面的结论，并**在返回值里写明这一点**，另外补两件 ast 能做到的事：

1. **危险节点扫描**：`import os/sys/subprocess`、`eval/exec/compile/__import__/open` 调用、
   `__class__/__bases__/__subclasses__/__globals__` 等逃逸跳板。
2. **结构统计**：函数数、类数、循环数、最大嵌套深度——给模型一个有信息量的结论，
   而不是干巴巴一句"语法正确"。

> **与 Calculator 的机制差异**：Calculator 是**求值**，必须白名单（不在白名单一律拒绝）；
> CodeExecutor 是**审查**，从不求值，所以可以用黑名单。黑名单在"审查并告警"场景是
> 合适的——漏报只是少一条告警，不会导致代码被执行，因为**根本没有执行路径**。

### 4.2 多步任务设计

四道多步题，每道至少 3 步（检索 → 计算 → 判定）：

| # | 任务 | 期望链路 | 正确答案 |
|---|---|---|---|
| M1 | 星尘X1 价格+运费，是否超预算 1000 | search → calc(899+68) → calc(967>1000) | 967，未超 |
| M2 | 追光S3 价格+运费，是否超预算 1000 | search → calc(1299+120) → calc(1419>1000) | 1419，超 |
| M3 | 磐石M2 + 微澜A1 合计（含各自运费） | search ×2 → calc(713+214) | 927 |
| M4 | 云雀Pro 银卡 95 折后含运费总价 | search → search(会员) → calc(459×0.95+0) | 436.05 |

M4 特意设计成需要**两次检索**（商品 + 折扣规则），且规则里写明"折扣仅作用于商品价格，
不作用于运费"——考察模型是否真的读了规则，而不是把折扣套在总价上。

## 五、Day31：工具调用 SFT

### 5.1 核心设计：一条轨迹 → 多条样本，每条在 Action Input 处截断

朴素做法是"一条完整轨迹 = 一条训练样本"，output 里含 Observation。
**这样训出来的模型会自己编造 Observation**——因为训练数据告诉它，写完 Action Input
之后就该接着写 Observation。而 Observation 必须由框架真正调用工具后回填。

正确做法：一条 n 步轨迹拆成 n+1 条样本。第 k 条样本的 assistant 内容 =

```
前 k-1 步（含各自 Observation，作为已知前缀）
+ 第 k 步的 Thought / Action / Action Input   ← 到此为止，不含 Observation
```

于是「**Action Input 之后就是 EOS**」这个模式被反复强化，模型学会写完就停。
最后再补一条以 Final Answer 收尾的样本。

这个拆法同时与推理时的 prefill 机制**精确对齐**：训练时学的正是
`P(下一步 | 已有前缀)` 这组条件概率，训练与推理完全同分布。

**校验结果：146 条样本中，0 条违反截断规则，0 条以 Observation 结尾。**

### 5.2 数据配比：含两类负样本

| 类型 | 目的 |
|---|---|
| 单步 calculator | 算术必调工具，不心算 |
| 单步 knowledge_search | 事实必查证，不编造 |
| 单步 code_check | 代码检查走对工具 |
| 多步 价格+运费+预算 | 验收标准❷：至少 3 步 |
| 多步 多商品 / 会员折扣 | 更长链路、两次检索 |
| **负样本：查不到** | 老实说没有，不编、不原样重试 |
| **负样本：无需工具** | 闲聊/自我介绍直接 Final Answer，**防止"见工具就调"** |

**内容即代码**（沿用 Week4 `make_self_built_pairs.py` 的做法）：所有轨迹由知识库真实
数据程序化生成，价格/运费/总价全部由 Python 现算，不手写数字——保证 100% 事实正确
且可复现，改知识库即自动同步。训练数据里的 Observation 也直接调用**真实工具**产生，
与线上完全一致。

### 5.3 超参与理由

| 参数 | 值 | 理由 |
|---|---|---|
| policy 起点 | `week4-dpo-merged` | 在已对齐模型上继续教工具调用 |
| `lora_rank` / `alpha` | 16 / 32 | Week3 最优是 r32，但那是 4684 条；146 条上 r32 会迅速过拟合 |
| `learning_rate` | 1e-4 | 与 Week3 最优组一致 |
| `num_train_epochs` | **8** | 146 条 ÷ 等效 batch 8 ≈ 17 步/轮；3 轮才 51 步学不会格式，8 轮 ~136 步与 Week3 的 108 步同量级 |
| `cutoff_len` | **2048** | 实测单条最长 2046 字符，1536 会截断掉多步轨迹尾部的 Action Input——而那正是要学的目标 |
| `packing` | **false** | ①同 Week4，打包破坏轨迹边界；②**打包会把下一条样本接在 EOS 位置，直接抹掉"写完就停"这个核心训练信号** |
| `seed` | 42 | 全项目一致 |

## 七、Day32：Agent 错误模式分析

完整报告见《Agent错误模式分析报告.md》，此处摘核心。

### 7.1 死循环的根因：训练数据里 Action Input 与 Observation 不自洽

ReAct 的 `Action Input` 是**单行**的——模型无法在其中输出真换行，只能写转义的 `\n`。
构造训练数据时这一点处理对了，但 **Observation 却是用「真实换行的原始代码」算的**：

| | 训练数据（v1） | 线上真实 |
|---|---|---|
| Action Input | `def add(a, b):\n    return a + b`（字面 `\n`） | 同左 |
| Observation | `语法正确（共 2 行）` ← 用**真换行**算的 | `语法错误：…line continuation…` |

模型学到的因果是"发这个 Action Input → 得到『语法正确』"。线上却拿到语法错误，
与习得预期冲突；模型不认为是自己写错了，于是**原样重试**，必然得到同样错误 → 闭环。

**修复**：让工具接受转义换行（模型受 ReAct 格式所限必然这么写，这与 Calculator
磨平全角字符是同一类输入归一化），同时让数据生成器**用 Action Input 里那个一模一样的
字符串**去调真实工具算 Observation。

### 7.2 一条可复用的原则

> 训练数据里的 Observation，必须由「Action Input 里那个一模一样的字符串」喂给
> **真实工具**产生，绝不能用另一份等价但不同形的输入去算。

任何"等价改写"（转义、去空格、格式化）都会在训练与推理之间制造分布裂缝，
而这种裂缝在 loss 上不可见，只会在端到端行为上炸开。

### 7.3 各失败模式的治法

| 失败模式 | 治法 | 实测 |
|---|---|---|
| 该调计算器却心算 | SFT | ✅ M2 修正 |
| 重复调用 | SFT | ✅ M3 从 5 步降到 3 步 |
| 死循环 | **训练数据自洽** + `max_iterations` 兜底 | ✅ 清零；上限保证复发时能收敛而非挂死 |
| 幻觉/表述错误 | SFT | ✅ M4 修正 |
| 选错工具 | 改工具名 / 描述 | ✅ 45 次运行 0 次误用 |

**工具命名的验证**：第三个工具取名 `code_check` 而非任务书里的 `CodeExecutor`——
45 次运行中没有任何一次模型试图用它求代码运行结果。名字的字面语义确实主导工具选择。

### 7.4 方法论发现：判定口径会系统性低估错误率

宽松判定（"期望值出现在答案里"）给 `dpo` 打 9/9，严格判定只有 8/9——差距正是 M4 那条
"含正确数字但表述错误"的答案。若只看宽松口径，会得出"微调前就已完美"的结论，
**既错过真实错误，也测不出微调的收益**。

### 7.5 一个被自己推翻的预判

分析初期我判断 M4 是**结构性局限**（ReAct 的 scratchpad 无待办清单机制，答完第一问
就认为完成，需在编排层做任务分解）。**实测推翻了它**——修复数据后的模型两个事实
都答对了。**能靠数据解决的问题，不要急着归因到架构。**
