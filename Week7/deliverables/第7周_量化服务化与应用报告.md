## 一、环境：三个 venv，以及一次依赖夹击

WSL 里最终建了**三个** venv，不是一个。原因是三方依赖互相夹击：

| venv | 关键包（2026-08-21 实测） | 为什么必须独立 |
|---|---|---|
| `~/venvs/vllm` | vllm 0.27.1 / torch 2.13.0+cu130 / compressed-tensors 0.17.0 | vLLM 把 torch 钉死在编译时那个版本（CUDA 扩展与 torch ABI 绑定） |
| `~/venvs/quant` | llmcompressor 0.13.0 / GPTQModel 7.3.4 / transformers 5.14.1 | 量化工具链要新 transformers |
| `~/venvs/lf` | llamafactory 0.9.6.dev0（`--no-deps`） | LF 0.9.6 发布时 transformers 还在 4.x，与 gptqmodel 的诉求互斥 |

量化和服务本就是先后两个阶段，无需共享运行时——沿用 Week5 `.venv-vlm`、Week6 `.venv-agent`
的同一条隔离思路。

两处安装期修正：

- `gptqmodel` 导入时报 `No module named 'torchvision'`——它的 import 链里带了视觉模型分支。
  补装 `torchvision 0.28.0+cu130`（pip 自动对上 torch 2.13.0+cu130）后正常。
- **`~/venvs/lf` 是被逼出来的第三个环境。** 原计划 LF 和量化工具同居 `~/venvs/quant`，
  但 LF 是用 `--no-deps` 装的，pip 没施加版本约束，而该环境里 `transformers` 已被
  gptqmodel 拉到 5.14.1。`import llamafactory` 能过，**但导出路径能不能过是另一回事**。
  于是单开 `~/venvs/lf` + `DISABLE_VERSION_CHECK=1`，
  并且**用「真的跑通一次导出」来验证，而不是用「import 不报错」来验证**。

> 这条教训与 Week6 的「训练指标健康 ≠ 线上行为正确」是同一类：
> **可用性只能由端到端的真实执行来证明，不能由某个便宜的代理指标来证明。**

## 二、Day34：校准集构造 + AWQ 量化

### 2.1 校准集：两个池子严格不相交

`build_calib_data.py` 先把 Week4 的 1221 条原始偏好样本切成互斥的两池
（校准 921 / 留出 300），再各自按 chat template 拼成长文档：

| 产物 | 条数 | token 长度 (min / 中位 / max) | 用途 |
|---|---|---|---|
| `data/calib.json` | 256 | 1334 / 1560 / 2570 | AWQ + GPTQ 校准 |
| `data/ppl_eval.json` | 48 | 1333 / 1508 / 2692 | Day35 困惑度评测 |

**为什么必须拼成长文档**：LF 的 `_get_quantization_dataset()`
（`quantization.py:60-66`）随机抽一条样本，**只接受 token 数严格大于
`export_quantization_maxlen` 的样本**，100 次重试全落空就抛
`Cannot find satisfying example`。单条聊天样本只有几百 token，直接喂必炸。
这里按 1.3× maxlen 拼接并在生成时复核长度，避免等到导出跑一半才失败。

**两条路径的校准预算严格对齐**：AWQ（`quantize_awq.py`）与 GPTQ
（`export_gptq_w4.yaml` 的 `export_quantization_nsamples: 128 / maxlen: 1024`）
都实取 **128 篇 × 1024 token**。校准预算不一致的话，Day35 的质量对比就掺进了
「谁看的数据多」这个混淆变量，结论不成立。

### 2.2 一次真的抓到 bug 的冒烟测试

`quantize_awq.py --check` 这个冒烟开关本来只是保险，结果抓到一个**静默失效**：

llm-compressor 0.13.0 把 AWQ 拆成了两个 modifier——`AWQModifier` 只负责搜索等价缩放因子，
真正压到 4-bit 的是 `QuantizationModifier`。而旧的
`from llmcompressor.modifiers.awq import AWQModifier` 现在是**废弃 shim，返回的是一个 list**。
原脚本用 `hasattr(recipe, "group_size")` 探测后赋值——对 list 恒为 False，
于是 `--group-size` **静默失效，不抛任何异常**。

已改用新 API 显式构造两段式配方。顺带查清 `group_size` 不是 modifier 的字段而在 scheme 里：
`preset_name_to_scheme("W4A16", ["Linear"])` 本身就是 num_bits=4 / group_size=128 /
symmetric=True，128 即预设值；偏离 128 才需要展开成 `config_groups`。

> **教训**：`hasattr` 式的「兼容性探测」在上游 API 变动时，会把错误变成**静默无操作**——
> 比直接抛异常难发现得多。这类地方应该显式断言版本，或者显式构造对象。
> 这和 Week6「Action Input 与 Observation 不自洽」是同一族问题：**不报错的错误最贵。**

### 2.3 AWQ 实测

```
[env]    llmcompressor=0.13.0
[calib]  128 条样本, maxlen=1024
[recipe] ['AWQModifier', 'QuantizationModifier']  group_size=128
[ok]     耗时 4.7 分钟；磁盘 5.76 GB -> 1.92 GB（降 66.6%）
```

日志里一条值得记的告警：`36 mappings were skipped due to incompatible shapes`。
这是 AWQ 自动推断 smooth 映射时跳过了形状对不上的层（如 GQA 下 q/k/v 输出维不一致的组合），
属于预期行为，不是失败——但如果不知道它存在，看到 36 条 WARNING 容易误判成量化没做全。

## 三、Day35：GPTQ 导出 + 三方对比

### 3.1 GPTQ 导出

```
(~/venvs/lf) $ DISABLE_VERSION_CHECK=1 python -m llamafactory.cli export Week7/configs/export_gptq_w4.yaml
02:28:01 开始 → 02:35:50 结束，耗时 7 分 49 秒
all params: 311,314,432        ← 量化打包后统计到的参数量（int4 已不按 fp 计）
```

### 3.2 三方对比结果（全部实测，2026-08-21）

| 精度 | 权重显存 (GiB) | 相对 FP16 降幅 | 困惑度 (中位) | 相对 FP16 | tok/s (batch=1) | tok/s (并发16) | 量化耗时 |
|---|---|---|---|---|---|---|---|
| FP16 | 5.79 | — | 5.231 | — | 119.84 | 1393.81 | — |
| AWQ  | 1.95 | **66.3%** | 5.639 | +7.80% | **226.54** | **2018.92** | 4.7 min |
| GPTQ | 1.94 | **66.5%** | **5.416** | **+3.55%** | 209.50 | 1475.34 | 7.8 min |

> 口径：权重显存来自 vLLM 启动日志的 `Model loading took ... GiB`；困惑度用同一个 vLLM
> 服务的 `/v1/completions` + `prompt_logprobs=0` 在 32 篇留出文档上算，取中位数；
> 吞吐分 batch=1 顺序与并发 16 两组，`max_tokens=256`。
> **PPL 与吞吐走同一个服务端接口**——若 PPL 用 HF transformers 算、吞吐用 vLLM 测，
> 差异里就掺进了两套 kernel 的实现差异，唯一变量就不再是量化算法本身。

### 3.3 `nvidia-smi` 抹平的那一侧：量化真正买到了什么

同一个 `--gpu-memory-utilization 0.85`（三次测量必须相同，否则吞吐不可比），
三种精度的启动日志：

| 精度 | 权重 | 可用 KV cache | KV cache 容量 | 32K 上下文下的最大并发 |
|---|---|---|---|---|
| FP16 | 5.79 GiB | 13.23 GiB | 385,280 tokens | 11.76× |
| GPTQ | 1.94 GiB | 17.69 GiB | 515,328 tokens | 15.73× |
| AWQ  | 1.95 GiB | **18.13 GiB** | **528,176 tokens** | **16.12×** |

**同样一张 4090，AWQ 比 FP16 多出 4.9 GiB 的 KV cache、多 37% 的并发容量。**
这才是量化在服务化场景的真实收益——不是「进程更小」，而是**「同样的显存里能塞下更长的
上下文、更多的并发请求」**。用 `nvidia-smi` 量进程总显存，正好把这个收益量成了 0。

### 3.4 三条值得记的观察

**① 66% 的降幅不是 4 倍，原因在 `lm_head`。**
5.79 → 1.94 只有约 3 倍，因为 `lm_head` / embedding（tied，151936×2048 ≈ 0.31B 参数）
保持 fp16 未量化，只有约 2.6B 的线性层被压到 4-bit。这正是 `quantize_awq.py` 文件头
事先预判的「约 2.2GB」，实测 1.95GB。**能事先算出来的数，就该事先算，用来校验实测。**

**② GPTQ 的质量明显好于 AWQ，代价是量化耗时接近翻倍。**
PPL 劣化 +3.55% vs +7.80%，耗时 7.8min vs 4.7min。这与两者的算法差异完全一致：
GPTQ 用 Hessian 做逐列误差补偿（**改权重值**去补残差），AWQ 只做等价缩放
（**改权重尺度**，不补残差）。多花一倍算力换更小的量化误差，对一次性的离线量化是划算的。

**③ 「4-bit 在高并发下可能反而更慢」的事前预判，被数据推翻了。**
`bench_quant.py` 文件头写过这个预期：低 batch 是显存带宽瓶颈（4-bit 赢），
高并发转向算力瓶颈，反量化开销摊不掉，4-bit 可能反输。实测并发 16 时 AWQ 仍有
**1.45 倍**优势——说明这个规模下并发 16 远没把 4090 推到算力瓶颈，仍在带宽区间。
要复现那个拐点，得把并发继续往上推。

另一个现象更有意思：**AWQ 在并发下大幅反超 GPTQ（2018 vs 1475），而 batch=1 时两者接近
（226 vs 209）**。两者位宽、group_size 完全相同，差异只能来自 kernel 实现——
compressed-tensors 走的是 Marlin 路径，GPTQ 走 gptq_v2。
**这条差异属于「推理引擎」而非「量化算法」，选型时不该记到算法头上。**

## 四、Day36：vLLM 服务化 —— 三个坑都不是模型问题

服务能起来之前连撞三次，全部与模型、权重、量化无关：

| 症状 | 根因 | 解法 |
|---|---|---|
| `RuntimeError: UVA is not available` | vLLM 0.27.1 默认用 V2 model runner，它的 `UvaBuffer` 依赖 UVA；而 `is_uva_available()` 实为 `is_pin_memory_available()`，vLLM **在 WSL2 上默认关闭 pinned memory**（怕小幅性能回退） | `VLLM_WSL2_ENABLE_PIN_MEMORY=1`（本机内核 6.18.33 ≫ 门槛 4.19.121） |
| `Could not find nvcc` | 别被误导成「要装 CUDA toolkit」。注意力后端是 FLASH_ATTN（wheel 自带预编译），崩的是**采样器**：FlashInfer 的 top-k/top-p 是 **JIT 编译**的，运行时才现场 nvcc 编 kernel | `VLLM_USE_FLASHINFER_SAMPLER=0`，退回 PyTorch 原生采样 |
| LF 导出全链报错 | 见 §一：LF 与 gptqmodel 对 transformers 的要求互斥 | 第三个 venv + `DISABLE_VERSION_CHECK=1`，并用真跑通导出来验证 |

第二条的关键是**分清「注意力后端」和「采样器」**：报错里出现 nvcc，第一反应是装
3GB 的 CUDA toolkit；但日志明写着 `Using FLASH_ATTN attention backend`，
注意力这条路是有预编译 kernel 的，真正 JIT 的是采样器那一步。
**看懂报错发生在哪一层，比看懂报错文本本身更重要。**

两个 env 已固化进 `serve_vllm.sh`。需要注明：`VLLM_USE_FLASHINFER_SAMPLER=0` 的性能影响
对三种精度**同等施加**，不影响 §三 的相对结论；但绝对吞吐值不应拿去和原生 Linux 的数字比。

`--served-model-name` 三种精度统一成 `qwen3b`：切换后端时客户端代码一行不用改，
量化种类靠端口和日志区分。

**客户端 Demo（`client_demo.py`）实测通过**，非流式 + 流式各一遍，`/v1/models`
正常返回。用官方 `openai` SDK 而不是手写 requests——打通它等于同时证明了
「任何 OpenAI 生态的工具（LangChain / OpenWebUI / 自研前端）都能零改造接上」，
这才是「OpenAI 兼容」四个字的价值。实测 **TTFT = 0.033s**。

## 五、Day37：Gradio 前端 —— 同一个代理坑要堵两次

`app.py`（Windows 侧 `.venv`，gradio 5.50.0）对接 WSL 里的 vLLM。
最花时间的不是 UI，是本机系统代理导致的两处 502。

### 5.1 坑一：`openai` SDK 打 127.0.0.1 却 502

症状很有迷惑性：`curl` 打 `127.0.0.1:8000` 返回 200，端口转发一切正常，
但 SDK 一调就 `InternalServerError: Error code: 502`。链条是：

1. `openai` SDK 底层用 httpx；httpx 在 `trust_env=True`（默认）时调
   `urllib.request.getproxies()` 取代理配置；
2. 该函数在 Windows 上会去读**注册表**里的系统代理
   （本机 `HKCU\...\Internet Settings → ProxyServer=127.0.0.1:7897`）；
3. 注册表里其实有 `ProxyOverride` 白名单，包含 `localhost` 和 `127.*`，
   但 `getproxies()` **不返回 `'no'` 键**，httpx 也不实现 ProxyOverride 的绕过逻辑——
   于是它把发往 `127.0.0.1:8000` 的请求塞进了代理，代理转不了 localhost，回一个 502。

**所以这不是「服务没起来」，而是「请求绕了一圈没到服务」。**
解法：`httpx.Client(trust_env=False)`。比要求用户去改系统代理设置健壮得多——
毕竟目标是「不懂深度学习的同学也能用」。

### 5.2 坑二：Gradio 自己请求自己，也被劫走

`launch()` 时 Gradio 会**请求它自己**的 `/gradio_api/startup-events` 做自检，
同一个系统代理把这个 localhost 请求也劫走，于是抛
`Couldn't start the app because '.../startup-events' failed (code 502)`。

这次堵不到 httpx 参数上（是 Gradio 内部构造的 client），只能在**进程环境**层面堵：

```python
for _k in ("NO_PROXY", "no_proxy"):
    os.environ[_k] = "localhost,127.0.0.1,::1"
```

且必须在 `import gradio` **之前**。为什么设 `no_proxy` 就能根治：
`getproxies()` 的实现是 `getproxies_environment() or getproxies_registry()`——
只要环境变量里有任何代理相关的键（含 `no_proxy`），前者返回非空，
**注册表那一路就整个不读了**。我们只填 `no_proxy` 不填 `http_proxy`，
结果就是「什么代理都不走」，正是本地服务想要的。

> 一个坑要在两个层面各堵一次（**我们发出的请求**用 `trust_env=False`，
> **框架内部发出的请求**用环境变量），因为它们的 client 不是同一个。

### 5.3 四个 UI 侧的设计取舍

| 取舍 | 理由 |
|---|---|
| 后端切换做成**下拉框**，而不是起两个应用 | 24GB 塞不下 3B 文本 + 7B VLM 同时常驻（VLM fp16 单独就要约 16GB），两个服务是**互斥槽位**（8000 / 8001）。UI 把这件事藏起来，用户只看到「聊天模型 / 看图模型」；连不上时给出**能直接照抄的启动命令**，而不是甩一个 `Connection refused` |
| 自己维护一份 `api_history`（`gr.State`），不回传 Chatbot 内容 | Gradio 的 Chatbot 为渲染会把图片存成 `{"path": ...}` 这类前端结构，拿去喂 API 需要反向解析，Gradio 一升版就碎。**渲染归渲染、协议归协议**，多写二十行换掉一整类「升级后聊天记录错乱」的 bug |
| 图片走 **base64 data URI** 而不是传路径 | vLLM 在 WSL2、Gradio 在 Windows，两者**不共享文件系统视图**（`C:\Users\...` vs `/mnt/c/Users/...`），传路径必然找不到文件。内联字节跨进程 / 跨文件系统 / 跨机器都成立，代价是请求体涨约 33%，本地单用户无所谓 |
| 参数滑块**收窄取值范围** | `temperature` 上限 1.5 而非 2.0（再高 3B 开始胡言乱语），`top_p` 下限 0.1（更低退化成近似贪心）。**面向非专业用户，就不该给出能调出灾难的档位** |

**实测通过**：`serve_awq.log` 里记录了 2026-08-21 03:16 前端发起的多次
`GET /v1/models`（探活）与 `POST /v1/chat/completions`（两轮流式对话）全部 200。

### 6.1 实测：`vl` 档起服务 + 图文问答（`serve_vl.log` / `vl_smoke.log`）

```
Model loading took 15.67 GiB and 114.56 seconds     ← drvfs 首次加载，约 2 分钟
Available KV cache memory: 2.3 GiB
Maximum concurrency for 8,192 tokens per request: 5.25x
```

用 Week5 的评测图 `eval_000.png` 走 OpenAI 兼容接口做流式图文问答（base64 data URI，
`temperature=0`），模型正确读出了图中训练面板的**任务名、基座模型、DoRA 秩与 alpha、
学习率、批大小、轮数、进度 93/180、loss 1.2820、显存 9.9GB、剩余时间**——
细粒度 OCR 与结构化理解都对上了。**TTFT = 0.380s，总耗时 2.85s。**

三个数字值得和 §三.3 的文本模型并排看：

| | 3B-AWQ（文本） | 7B-VL（多模态，fp16） |
|---|---|---|
| 权重 | 1.95 GiB | **15.67 GiB** |
| 可用 KV cache | 18.13 GiB | **2.3 GiB** |
| 最大并发 | 16.12×（@32K） | 5.25×（@8K） |
| TTFT | 0.033 s | 0.380 s |

**「两个服务互斥槽位」这条设计不是保守，是算出来的：**
VL 单模型就吃掉 15.67 GiB 权重，24GB 卡上剩给 KV cache 的只有 2.3 GiB；
再并排一个 fp16 的 3B（5.79 GiB）直接放不下。
而如果 VL 也做 4-bit 量化，按本周 66% 的降幅推算权重可压到约 5.3 GiB，
两个服务就有同时常驻的空间——**这正是下周（第 8 周）「更激进量化 / 蒸馏」的直接动机。**

## 九、本周方法论小结

三条可复用的：

1. **测量口径决定结论。** 同一件事（量化省不省显存），用 `nvidia-smi` 量得出「不省」，
   用启动日志量得出「省 66%」。做基准之前先问：这个数字是被谁决定的？有没有被别的机制抹平？
2. **不报错的错误最贵。** `hasattr` 探测在上游 API 变动时静默失效；`^` 在 Python 里是异或
   （Week6）；`import` 成功不代表导出路径能跑。凡是「失败会静默」的地方，都该换成显式断言。
3. **事前预判要写下来，然后让数据去推翻它。** 本周写下的两条预判——「4-bit 高并发可能更慢」
   与「Gemma-4 不在 registry 里」——都被实测推翻了。写下来才有得被推翻；
   推翻了如实记录，不回头修改预判。（这条从 Week6 §6.4 延续。）
