# Day26：VLM 轻量微调（冻结 ViT，只训 LLM 侧低秩适配）

## 一、任务设计：为什么没用任务书的"写产品描述"

任务书 26.1 的例子是「请根据这张图写一段产品描述」。
问题在于验收 ❸ 要求「微调后有**明显效果提升**」——**产品描述是主观生成任务，微调前后没法客观打分**，
只能人打分，20 个留出样本说不清是提升还是噪声。

换成可客观打分的窄任务：**训练平台截图 → 团队规范的实验记录卡**。
20 条留出图 × 11 个字段 = 220 个字段逐个和真值精确比对。

### 第一版设计失败了（如实记录）

最初 11 个字段全是「照抄」型（从截图里读出来即可）。实测 Qwen2.5-VL-7B
**基线字段准确率就有 ~92%**——微调最多再涨 8 个点，且这 8 个点还可能是格式波动，
**测不出 LoRA 的价值**。

第二版把字段分成两类：

| 类别 | 字段 | 基座能不能自己做对 |
|---|---|---|
| **照抄型**（8 个） | 任务ID、基座模型、训练方式、学习率、进度、当前loss、显存占用、状态 | 能，实测 91.9% |
| **派生型**（3 个） | 进度百分比、剩余步数、健康状态 | **不能** |

派生型为什么基座做不到：
- **进度百分比 / 剩余步数**：需要算术（`93/180 → 52%`、`180-93=87`），且要求特定取整/格式
- **健康状态**：`状态==失败` 或 `loss≥1.0` 或 `显存≥20.0 GB` → 需关注，否则正常。
  **这条规则只存在于 200 条训练数据里，instruction 里不给。** 基座只能猜。

> **这是本天最重要的方法论**：评测集设计时先问「基座本来就会吗」。
> 只有基座不会的部分，才能测出微调真正学到了什么。

### 防数据泄漏

训练集（200 条）与留出集（20 条）用两条**独立随机流**生成（seed 42 / 10042），
图片内容、版式、配色都不重叠。同一个脚本 `build_vlm_sft_data.py` 一次生成图和真值，
保证真值 100% 准确（不需要人工标注，也就没有标注噪声）。

## 二、为什么冻结 ViT

三条依据，按重要性排：

1. **参数占比**：视觉塔只占 Qwen 总参数的 7.6%（632M / 8292M）。
   VLM 的看图能力主要来自 projector 的对齐质量，不是视觉塔容量（Day22 §三）。
2. **数据量不匹配**：ViT 是在几十亿图文对上预训练的通用特征提取器，
   **200 条数据去动它只会破坏表征**（灾难性遗忘）。
3. **任务性质**：要教的是「看到这类图该用什么格式/规则说话」——那是 LLM 侧的事，
   不是「看得清不清楚」的问题。图本来就看得清（基座照抄型 91.9%）。

配置里两行：
```yaml
freeze_vision_tower: true
freeze_multi_modal_projector: true
```
LF 的 `find_all_linear_modules` 会自动把 `visual.patch_embed` / `visual.blocks` / `visual.merger`
排除出 `lora_target`，训练日志里能看到：

```
Set vision model not trainable: ['visual.patch_embed', 'visual.blocks'].
Set multi model projector not trainable: ['visual.merger'].
trainable params: 40,370,176 || all params: 8,332,536,832 || trainable%: 0.4845
```

## 四、★ 踩坑：Windows 上显存贴顶不会 OOM，而是静默劣化 38 倍

第一次训练在 **step 20 之前是 5.4 s/step，step 21 起掉到 205 s/step**，
trainer 把 ETA 从 4 分钟改成 1 小时 19 分，最终中断。

这不是"慢了一点"，是 NVIDIA 驱动在 WDDM 下把超出显存的部分放进系统内存
（**sysmem fallback**）。**Linux 上会直接 OOM 报错，Windows 上只是变慢**——
不报任何错，日志里没有任何异常，极难定位。

### 三条应对

| 手段 | 效果 |
|---|---|
| 降 `image_max_pixels`（589824 → 451584，视觉 token 680 → 580） | ✅ 有效，是主要杠杆 |
| **`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`** | ❌ **反效果，见下** |
| 训练时盯 `nvidia-smi`，速度掉一个数量级就是这个原因 | ✅ 唯一的实时信号 |

### 重跑时的关键观察：劣化是随时长累积的，不是某一步触发的

降分辨率后重跑，步速是这样走的：

| 阶段 | 步速 |
|---|---|
| step 1–20 | ~12 s/step |
| step 20–40 | ~13 s/step |
| step 50–55 | **~35 s/step** |
| 全程 | 69 步 / **18 分 01 秒**，跑完了 |

**同样在劣化，只是没崩到 200+。** 说明这个机制是**显存碎片随训练时长持续增长**导致的，
降分辨率没有消除它，只是把起点压低、让训练在崩溃之前结束。

> 真正的解法是**留出显存余量，而不是卡着上限跑**。
> 判据三件套：速度掉一个数量级 + 显存贴着上限 + GPU 利用率仍 98% 且 `clocks_throttle_reasons.active = 0x0`
> ——三条同时出现就是 sysmem fallback，不是算力不够也不是过热降频。

> **`expandable_segments` 在 Windows + torch 2.6 上是负优化。**
> 实测开启后 allocator 一上来就把 23.7/24 GB 占满，步速从 5.4 s/step 变成
> 23 → 31 → 38 s/step **且持续恶化**，比不设还差得多。
> 这个参数在 Linux 上是抗碎片的标准手段，**不要跨平台照搬**。

### 另一个坑：`save_steps` 必须小于总步数

第一次配置写 `save_steps: 100`，而总步数只有 69 —— **等于全程不落盘**，
中断后 20 分钟训练全部作废，连 `resume_from_checkpoint` 都没得续。
改成 20（总步数的 ~1/3），step 20/40/60 各存一次。

**总步数少的小任务，save_steps 要按总步数比例设，不能照抄大任务的默认值。**

## 五、超参与显存关系（VLM 特有）

| 参数 | 值 | 说明 |
|---|---|---|
| `image_max_pixels` | 451584（672²） | **训练显存的第一杠杆**，比 cutoff_len 影响大得多 |
| `cutoff_len` | 1536 | 580 视觉 + ~80 指令 + ~90 目标 ≈ 750，1536 足够 |
| `per_device_train_batch_size` | 1 | 24GB 上 bf16 全参加载已占 16.6GB |
| `gradient_accumulation_steps` | 8 | 等效 batch 8 |
| `gradient_checkpointing` | true | 必开 |

一张图 580 个视觉 token，而指令 + 目标加起来才 ~170 个——
**VLM 微调的序列长度主要由图片决定，不是由文本决定。**

## 六、结果

训练：69 步 / 3 epoch / **18 分 01 秒**；train_loss 0.0612 → 0.0039；
eval_loss step25 0.00922 → step50 0.00514 → step69 0.00511（step50 后持平，3 epoch 正合适）。

| 指标 | base | lora | 提升 |
|---|---|---|---|
| **字段准确率** | 77.7% | **98.2%** | **+20.5%** |
| 　├ 照抄型 8 字段 | 91.9% | 100.0% | +8.1% |
| 　└ **派生型 3 字段** | 40.0% | **93.3%** | **+53.3%** |
| **整条 11 字段全对率** | 0.0% | **80.0%** | **+80.0%** |
| 格式合规率 | 100.0% | 100.0% | +0.0% |
| 平均延迟 | 4.22s | 6.97s | +2.75s |

**三类提升要分开读**（完整版见 `deliverables/微调前后对比表.md`）：

1. **派生型 +53.3% 才是 LoRA 的价值**——「健康状态」规则不在指令里，基座只能猜（45%≈瞎猜），
   微调后 90%。LoRA 干的事是**把领域约定编码进权重**。
2. **照抄型只 +8.1% 且符合预期**——ViT 冻结了，视觉表征根本没变。
   这反过来印证 Day22 的参数拆解：**LoRA 改的是语言侧怎么组织输出，不是眼睛怎么看**。
3. **延迟 +65% 不是 LoRA 的计算开销**（40M 参数可忽略），是微调模型**输出更完整**
   （base 常漏字段或提前停）。**评估延迟必须和输出长度一起看**——和 Day23 里 Gemma"慢"是同一个陷阱。

唯一没做满的是「进度百分比」90%：`176/600 = 29.33%`，真值 29%，模型给 30%——
**取整约定没学透，不是看错数**，200 条数据里区分四舍五入/向下取整的样本不够。
