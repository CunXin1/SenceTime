# Day23：图文推理与能力边界探索

## 一、问题矩阵怎么设计

任务书要求「5 类问题 × 5 张图 = 25 条」。本周做成 **5 类 × 6 张图 = 30 条，两个模型各跑一遍 = 60 条**。

| 类别 | 提问模板要点 | 为什么这么问 |
|---|---|---|
| 描述内容 | 「描述画面里有什么，包括数量」 | **强制报数量**才能暴露计数幻觉；不问数量模型会含糊过去 |
| 提取文字 | 「逐字抄出图中所有文字，不要翻译不要润色」 | 「不要翻译」这句必须写，否则日文牌会被直接译成中文，OCR 精度就测不出来 |
| 解释图表 | 「X 最高的是哪一行？它的 Y 和 Z 分别是多少？」 | 有唯一正确答案，可精确打分；且需要**跨列取数**，比单值抽取难一档 |
| 评价美学 | 「从构图/色彩/信息层次三角度评价，并指出一处可改进」 | 任务书要求；实测无区分度，见下 |
| 推理隐含信息 | 「从图里能推断出什么没有直接写出来的信息？」 | 看模型是否给出视觉依据，还是纯凭常识编 |

问题写在 `build_questions.py` 里而不是手敲 JSON，是为了**同一套问题对两个模型逐字一致**——提示词差一个字，对比就不成立。

## 二、执行

```powershell
.\.venv-vlm\Scripts\python.exe Week5\code\vlm_infer.py            # 两模型 × 30 问
```

`vlm_infer.py` 每条记录除答案外还落盘：视觉 token 数、提示 token 数、生成 token 数、延迟、峰值显存。
**这些运行时指标和答案一样重要**——Day23 的核心结论（OCR 精度差距源于视觉 token 预算）就是靠视觉 token 数这一列推出来的，光看答案只能得到"Gemma 读错了"这种没有解释力的结论。

支持 `--resume`：已有结果的 (模型, 问题) 组合跳过。素材是分批补齐的（3 张自动生成 + 3 张真实照片人工放入），没有断点续跑就得整批重来。

## 三、结果与结论

完整分析见 `deliverables/Day23_能力边界分析.md`，这里只记方法论层面的三点。

### 1. 打分必须客观化

「模型答得好不好」如果靠人打 1~5 分，60 条记录的结论就是印象。做法是从 `ground_truth.json` 里挑出**可精确匹配的硬事实**（数值、专名、题款原文共 23 条），逐条检查回答里是否出现：

| 模型 | 命中 | 命中率 |
|---|---|---|
| `Qwen2.5-VL-7B-Instruct` | 23/23 | 100% |
| `gemma-4-E4B-it` | 20/23 | 87.0% |

真值在跑推理**之前**就已固定在 `ground_truth.json` 里，不存在事后凑答案。

### 2. 一个被推翻的中间结论

看部分日志时下过判断：「Gemma 不能做日文 OCR」。**逐条比对后是错的**——Gemma 的假名 10 句全对，数字 12 个全对。真实差距是**形近字**：末→本、憲→意、崇敬→紫微、`l`→`1`。

教训：**看到"输出不对"先分清是「不能做」还是「做得不够细」**，两者的工程应对完全不同（前者要换模型，后者只要调 token 预算）。

### 3. 「评价美学」不该进评测集

两个模型都输出安全套话（"构图清晰、色彩简洁、建议增加对比色"），信息量低且高度雷同，无法分出高下。任务书列了这一类，做了，但结论是**它不适合用来评估 VLM 能力**——这本身也是一条有价值的结论。

## 四、踩坑

- **`max_pixels` 不设必 OOM**。Qwen 的视觉 token ≈ (H/28)×(W/28)，一张 4K 截图上万 token，注意力 O(n²)。本周设 `1280×28×28 ≈ 100 万像素`。
- **Gemma 慢在生成而不是看图**：平均延迟 22.9s vs Qwen 6.0s，但 Gemma 的视觉 token 只有 Qwen 的一半。原因是 Gemma 平均生成 591 字（Qwen 313 字）——它话多。**对比延迟时必须同时看生成长度，否则会把"话多"误读成"推理慢"。**
- CSV 里 `score / hallucination / note` 三列留给人工复核用，客观结论不依赖它们。
