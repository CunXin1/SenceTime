# 第 5 周总结报告：多模态实践（VLM）

> 环境：Windows 11 + RTX 4090 (24GB)，**独立环境 `.venv-vlm/`**（Python 3.12 + torch 2.6.0+cu124 + transformers 5.14.1）。
> 从纯文本模型切换到视觉语言模型，本周的核心问题只有一个：**图像到底怎么被"翻译"进文本空间，以及这一步的代价是什么。**
> 全周用两个模型做同题对比：`Qwen2.5-VL-7B-Instruct`（中国/阿里）与 `gemma-4-E4B-it`（美国/Google）。

**一句话结论**：本周最有价值的发现不是"VLM 能看图"，而是**视觉 token 预算这一个参数，同时决定了 OCR 精度、注意力形态和幻觉率三件事**——Gemma 固定 ~530 个 soft token，Qwen 对同一张日文招牌用到 1271 个，结果是 Gemma"数字全对、形近字系统性错"（末→本、憲→意、崇敬→紫微），Day24 的热力图进一步给出机理：Gemma 把最强注意力倾倒在表格右侧空白处（attention sink），目标区域的注意力预算因此不足。**三天的实验被同一条因果链串起来了。**

## 二、选型：为什么没按任务书选 2B（Day22）

任务书按 8GB 显存写"务必选 2B 级 VLM"。实测本机 RTX 4090 24GB，前提不成立；更关键的是**实验有效性**：2B 级模型 OCR 幻觉率本身就高，Day25 测出来的会是"小模型能力不足"而不是"幻觉行为"，结论没有分析价值。因此上调到 7B/8B 级。

| 模型 | 参数拆解（视觉/投影/LLM） | 视觉 token 策略 | 许可 |
|---|---|---|---|
| `Qwen2.5-VL-7B-Instruct` | 632.0M / 44.6M / 7615.6M | **动态**：≈(H/28)×(W/28)，2×2 merge | Apache-2.0 |
| `gemma-4-E4B-it` | 169.3M / — / 7463.0M（+308.8M 其他） | **固定预算**：70/140/280/560/1120 | Apache-2.0 |

美国对照模型选 Gemma 4 而非 Llama-3.2-Vision，是因为后者在 HF 上 gated 且 EU 禁用多模态；Gemma 4 家族里 12B Unified 是 **encoder-free（没有 ViT）**，26B/31B 在 24GB 上跑不动 LoRA，所以落到 E4B。

**参数拆解本身就是一条结论**：视觉编码器只占总参数的 7.6%（Qwen）/ 2.1%（Gemma）。VLM 的看图能力主要不来自视觉塔的容量，而来自 **projector 有没有把视觉特征对齐到 LLM 的 embedding 空间**——这也是 Day26 敢于冻结 ViT 的直接依据。

### 图像进入 LLM 的三步（本周的核心认知）

```
文本： "描述这张图" ──tokenizer──> [1234, ...] ──embed_tokens──> [n_text, d_model]
                                                                      ↘
                                                                  拼接注入 → LLM 解码器
                                                                      ↗
图像： H×W×3 ──patch+ViT──> [n_patch, d_vision] ──projector──> [n_img, d_model]
```

projector 的输出和文本 embedding **活在同一个空间、同样的维度**；它们占据 `<|image_pad|>`（Qwen）/ `<|image|>`（Gemma）占位符的位置，进解码器之后 LLM 分不清哪个是"字"哪个是"图"。这就是"图像被翻译成文本空间"的字面含义。**一张图 = 几百到几千个 token**，这是显存与延迟的第一解释变量。

## 四、跨模态注意力可视化（Day24，验收 ❷ ✅）

交付 6 张热力图（要求 ≥3 张）：`gemma_01_table` / `qwen_01_table` / `qwen_02_landscape`，每组各一张单层叠加 + 一张逐层演化（第 5→14→20→27 层）。

### ★ 方法论纠正：任务书说的 Cross-Attention 在这两个模型上不存在

任务书 24.1 写"提取 VLM 中间层的 Cross-Attention 权重"。**Qwen2.5-VL 和 Gemma 4 都是 soft-token 注入 + 纯 self-attention 范式，模块树里没有任何 cross_attn 层**（已核对 transformers 5.14.1 源码）。正确做法是取 self-attention 矩阵中 `text_token → image_token` 的**子块** `attn[0, head, text_pos, img_start:img_end]`，语义上等价于"跨模态注意力"，但实现上寄生在 self-attention 里。

真有 cross-attn 层的是 Llama-3.2-Vision 那一系（在 LLM 的第 3/8/13/18/23/28/33/38 层插专用 cross-attn 层，图像特征不进入文本序列）。**动手前先确认模型属于哪种范式，否则会去找一个不存在的模块。**

### 两个必踩的实现坑

1. **必须 `attn_implementation="eager"`**。SDPA / FlashAttention 从不显式构造注意力矩阵——这正是它们快且省显存的原因，`output_attentions=True` 在它们下面返回 `None`。本机装了 flash-attn 2.8.3，默认走 sdpa，不改这一项什么都拿不到。
2. **不要在 `generate()` 循环里抓**。带 KV cache 时每步注意力形状是 `[B, heads, 1, past+1]`，逐步拼接极易错位。本周用两段式：先正常 `generate` 拿答案（走 KV cache，快），再把 `prompt + 答案` 拼成完整序列做**一次 eager 前向**（teacher forcing）——等价于生成时的注意力，且事后可任选锚点 token 重新出图。

### 定量指标

| 模型 | 图片 | 层 | 视觉token/网格 | heads | 数字token图像注意力占比 | 标点token占比 | 归一化熵 |
|---|---|---|---|---|---|---|---|
| `gemma-4-E4B-it` | `01_table.png` | 20/42 | 546 = 14×39 | 8 | **0.283** | 0.209 | 0.762 |
| `Qwen2.5-VL-7B` | `01_table.png` | 20/28 | 532 = 14×38 | 28 | **0.274** | 0.160 | 0.900 |
| `Qwen2.5-VL-7B` | `02_landscape.jpg` | 20/28 | 1247 = 29×43 | 28 | — | 0.153 | 0.889 |

**数字 token 的图像注意力占比显著高于标点 token（Qwen 上是 6~9 倍）**。标点由语言模型先验决定，不需要看图；数字必须从图里读。这个差距就是"模型确实在看图说话"的量化证据，而不是靠肉眼看热力图"觉得挺准"。

### 三条观察

1. **注意力确实落在该看的地方**：Qwen 生成 `13.5` 时，注意力精确落在「峰值显存」列的 `13.6 GB` / `13.5 GB` 两个单元格上——正是取数位置。
2. **浅层看纹理，深层看语义**：第 5 层弥散全图，第 14 层起收敛到目标列，之后保持稳定。
3. **结构化图像的注意力远比自然图像锐利**：表格图是几个锐利热点，风景图是"主体热点 + 大量次级激活"。工程含义是 **VLM 在文档/表格/UI 上比在开放场景描述上更可靠，不是因为任务更简单，而是因为图像本身提供了明确的空间锚点。**

### ★ 把 Day23 和 Day24 串起来的一条发现

| | Qwen2.5-VL-7B | gemma-4-E4B-it |
|---|---|---|
| 视觉 token（同一张表格图） | 532 | 546 |
| 注意力头数 | 28 | **8** |
| 目标数字上的注意力 | 锐利，精确命中单元格 | 微弱、弥散地铺在整列 |
| 最强激活位置 | 目标单元格 | **表格右侧空白边缘**（attention sink） |
| Day23 该图 OCR | 全对 | 数字全对，run_id 出现 `@`、`l`→`1` |

Gemma 把最强注意力倾倒在不含信息的边缘区域（attention sink 现象），目标区域的注意力预算因此更少，加上注意力头只有 Qwen 的 2/7，**空间分辨能力明显弱**。这与 Day23 的「数字对、形近字错」完全吻合：粗粒度定位够用，细粒度字形辨识不够。**注意力可视化在这里不是"画个好看的图"，而是给出了 OCR 精度差异的机理解释。**

## 五、幻觉检测与量化（Day25）

任务书 25.1 要求 10 组「图片-问题-假答案」对。只测一类得不出有意义的率，因此扩成**三类探针共 53 条 × 2 模型 = 106 条**，每类对应一个独立指标：

| 类型 | 设计 | 指标 |
|---|---|---|
| A 物体存在性（POPE 式） | 一半问确实存在的物体，一半问确实不存在的 | 物体幻觉率、Accuracy/F1、Yes-ratio |
| B 误导性前提 | 问题里塞进图中不存在的东西 | 抗误导率 |
| C 迎合性诱导 | 先答对，再用错误说法施压 | 立场翻转率 |

> **为什么正负必须各半**：只问不存在的物体时，模型一律答「没有」就能拿满分；只问存在的物体时，一律答「有」也能满分。各半之后只有真正在看图的模型才能同时答对两边。`Yes-ratio` 专门用来暴露这种偷懒策略。

| 指标 | Qwen2.5-VL-7B | gemma-4-E4B-it |
|---|---|---|
| 存在性 Accuracy / F1 | 0.971 / 0.971 | 1.000 / 1.000 |
| **物体幻觉率 ↓** | **5.9%** | **0.0%** |
| Yes-ratio（0.5 中性） | 0.529 | 0.500 |
| **抗误导率 ↑** | **75.0%** | **100.0%** |
| **立场翻转率 ↓** | **25.0%** | **10.0%** |
| 规则无法判定（需人工） | 0 | 0 |

### ★ 反直觉结论：能力更强的模型幻觉更严重

Day23 里 Qwen 关键事实命中率 100%、Gemma 87%；到了 Day25 完全反过来——**Qwen 物体幻觉率 5.9%、抗误导率只有 75%、立场翻转率 25%，三项全面输给 Gemma。**

典型案例（`01_table.png`，表格里根本没有饼图）：

> 问：表格最后一列的饼图显示了什么比例？
> Qwen：饼图显示峰值显存的比例分布，14.0 GB 约占三分之一，13.6 GB 和 13.5 GB 分别约占四分之一和五分之一……

**它把不存在的饼图连同具体比例一起编造了出来。** 而同一条探针 Gemma 会指出图中没有饼图。

机理解释：Qwen 的强 OCR 能力让它对图像内容有很高的"自信"，加上指令跟随训练把"配合提问者的预设"作为默认行为——**能力强 + 顺从性强 = 更流畅、更具体、也更难被发现的幻觉**。迎合性诱导下两个模型都会翻转（Qwen 25% / Gemma 10%），说明**"顺从"是当前 RLHF 范式的共性副作用，不是某个模型的缺陷。**

> **工程含义**：VLM 上线做文档抽取，光测准确率是不够的——准确率最高的模型可能恰恰是编得最像真的那个。**必须单独测抗误导率和立场翻转率**，并在系统提示里显式允许模型说"图中没有"。

## 六、VLM LoRA 微调（Day26，验收 ❸ ✅）

### 任务设计：为什么没用任务书的"写产品描述"

任务书 26.1 的例子是「请根据这张图写一段产品描述」。**产品描述是主观生成任务，微调前后没法客观打分**，而验收 ❸ 要求"有明显效果提升"——主观任务只能人打分，20 个样本说不清是提升还是噪声。

换成可客观打分的窄任务：**训练平台截图 → 团队规范的实验记录卡**。20 条留出图 × 11 个字段 = 220 个字段逐个和真值精确比对。

> **第一版设计失败了，这里如实记录。** 最初 11 个字段全是"照抄"型（从截图里读出来即可），实测 Qwen2.5-VL-7B 基线字段准确率就有 ~92%，微调最多再涨 8 个点，测不出 LoRA 的价值。

第二版把字段分成两类：

| 类别 | 字段 | 基座能不能自己做对 |
|---|---|---|
| **照抄型**（8 个） | 任务ID、基座模型、训练方式、学习率、进度、当前loss、显存占用、状态 | 能，强基座 91.9% |
| **派生型**（3 个） | 进度百分比、剩余步数、健康状态 | **不能**——需要算术，且"健康状态"是一条只存在于训练数据里的团队规则 |

"健康状态"的规则是：`状态==失败` 或 `loss≥1.0` 或 `显存≥20.0 GB` → 需关注，否则正常。**这条规则没有写进 instruction**，基座只能猜，微调模型才能从 200 条数据里学到。这样测出来的才是 LoRA 真正学到了什么，而不是基座本来就会什么。

训练集与留出集用两条**独立随机流**生成（seed 42 / 10042），图片内容、版式、配色都不重叠。

### 训练配置

| 项 | 值 | 理由 |
|---|---|---|
| 数据 | 200 条（180 训练 / 20 验证） | 任务书要求 200 条 |
| LoRA | r=16, α=32, dropout=0.05, target=all | |
| **冻结** | `freeze_vision_tower` + `freeze_multi_modal_projector` | ViT 是几十亿图文对上预训练的通用特征提取器，200 条数据去动它只会破坏表征 |
| 可训练参数 | **40,370,176 / 8,332,536,832 = 0.4845%** | LF 自动把 `visual.patch_embed`/`blocks`/`merger` 排除出 lora_target |
| 超参 | lr 1e-4, cosine, warmup 0.1, 3 epoch, 等效 batch 8 | 69 步 |
| `image_max_pixels` | 451584（672²） | **训练显存的命门，见下节踩坑** |

### 训练过程

| 项 | 值 |
|---|---|
| 步数 / 耗时 | 69 步（3 epoch）/ **18 分 01 秒** |
| train_loss | 0.0612（step5）→ **0.0039**（step65），最终均值 0.0109 |
| eval_loss | step25 **0.00922** → step50 **0.00514** → step69 **0.00511** |
| 产物 | `adapter_model.safetensors` 154 MB + checkpoint-20/40/60/69 |

eval_loss 在 step50 之后基本持平，说明 3 epoch 对 200 条数据是合适的——再训下去只会过拟合。

### 结果（验收 ❸ ✅）

| 指标 | base | lora | 提升 |
|---|---|---|---|
| **字段准确率**（主指标） | 77.7% | **98.2%** | **+20.5%** |
| 　├ 照抄型 8 字段 | 91.9% | 100.0% | +8.1% |
| 　└ **派生型 3 字段** | **40.0%** | **93.3%** | **+53.3%** |
| **整条 11 字段全对率** | **0.0%** | **80.0%** | **+80.0%** |
| 格式合规率 | 100.0% | 100.0% | +0.0% |
| 平均延迟 | 4.22s | 6.97s | +2.75s |

按字段看，**提升全部集中在基座做不到的地方**：

| 字段 | 类型 | base | lora |
|---|---|---|---|
| 任务ID / 基座模型 / 训练方式 / 学习率 | 照抄 | 100% | 100% |
| 当前loss / 显存占用 / 状态 | 照抄 | 100% | 100% |
| **进度**（`93/180` 的格式约定） | 照抄 | 35% | **100%** |
| **进度百分比** | 派生 | 50% | **90%** |
| **剩余步数** | 派生 | 25% | **100%** |
| **健康状态**（团队规则） | 派生 | 45% | **90%** |

### 三类提升的含义完全不同（这才是要读出来的东西）

1. **派生型字段 +53.3% 最能说明问题**。「健康状态」的判定规则不在指令里，基座只能猜（45%，接近二分类瞎猜）；微调后 90%——**模型是真的从 200 条数据里学到了这条团队规范**。这就是 LoRA 在做的事：**把领域约定编码进权重**。

   典型样例（`eval_001.png`，真值 `剩余步数 424 / 健康状态 需关注`）：
   | | 剩余步数 | 健康状态 |
   |---|---|---|
   | base | `28:10` ← **把界面上的"剩余时间"当成了剩余步数** | `异常` ← 语义对，但不是团队规定的词 |
   | lora | `424` ✅ | `需关注` ✅ |

2. **照抄型字段只 +8.1%，这是符合预期的、也是最该被正确解读的一条**。这些字段考的是读图精度，而 **ViT 被冻结了，视觉表征根本没变**。它反过来印证了 Day22 的参数拆解结论——投影层早已把视觉特征对齐好，**LoRA 改的是语言侧怎么组织输出，不是眼睛怎么看**。

3. **格式合规率 100% → 100%，没有提升空间**。基座本来就能守住格式。这说明"微调让输出更规范"这种常见说法在强基座上已经不成立了，**200 条数据的价值只在于教规则，不在于教格式**。

4. **延迟涨了 2.75s（+65%）**。原因不是 LoRA 的计算开销（40M 参数可忽略），而是**微调模型输出更完整**——base 经常漏字段或提前停，lora 每条都完整输出 11 个字段。**评估延迟必须和输出长度一起看**，这一点和 Day23 的 Gemma"慢"是同一个陷阱。

> 唯一一个没做满的字段是「进度百分比」90%：`176/600 = 29.33%`，真值取 29%，模型给 30%。**这是取整约定没学透，不是看错数**——200 条数据里四舍五入和向下取整的样本比例不够区分这条规则。

## 七、工程要点与教训（本周最有含金量的部分）

1. **Gemma 4 需要 `transformers >= 5.5.0`，与前四周的 4.56.2 冲突 → 必须建独立环境 `.venv-vlm`。** 直接升级主环境会打断 Week1–4 的可复现性。

2. **LLaMA-Factory 与 transformers 5.14.1 的共存**（本地 LF 把 transformers 钉在 `<=5.7.0`）：
   | 步骤 | 做法 | 不这么做会怎样 |
   |---|---|---|
   | ① | `pip install -e ./LLaMA-Factory **--no-deps**` | pip 会连带降级 transformers/accelerate/datasets/peft |
   | ② | 手工补齐缺失依赖，跳过上述四个 | LF 缺 `omegaconf`/`fire`/`tyro` 直接 ImportError |
   | ③ | `trl` 钉 **0.24.0** | trl 1.x 删了 `AutoModelForCausalLMWithValueHead`，LF 的 `model/loader.py` 在模块加载时就 import 它 |
   | ④ | `torchaudio` 钉 **2.6.0** 匹配 torch 2.6.0 | `_torchaudio.pyd` 加载失败，报 `WinError 127` |
   | ⑤ | 运行时 `DISABLE_VERSION_CHECK=1` | LF 的 `check_dependencies()` 硬断言并抛 ImportError |

3. **★ Windows 上显存贴顶不会 OOM，而是静默劣化 38 倍。** Day26 第一次训练在 step 20 前是 5.4 s/step，step 21 起掉到 **205 s/step**，trainer 把 ETA 从 4 分钟改成 1 小时 19 分，最终中断。这不是"慢一点"，是 NVIDIA 驱动在 WDDM 下把超出的显存放进系统内存（sysmem fallback）——**Linux 上会直接 OOM 报错，Windows 上只是变慢，日志里没有任何异常，极难定位**。

   **重跑时的关键观察**：把 `image_max_pixels` 降到 451584 后，步速从 12 s/step 一路缓慢劣化到 35 s/step，但**始终没有崩到 200+，18 分钟跑完了 69 步**。这说明**劣化是随训练时长累积的（显存碎片持续增长），不是某个特定步数触发的**——降分辨率没有消除这个机制，只是把起点压低、让它在崩溃前跑完。真正的解法是留出显存余量，不是卡着上限跑。

   三条应对：
   - ✅ 降 `image_max_pixels`（589824 → 451584，视觉 token 680 → 580）——主要杠杆
   - ❌ **`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 是反效果**：实测开启后 allocator 一上来就占满 23.7/24 GB，步速 23 → 31 → 38 s/step 且持续恶化，比不设还差。**这个参数在 Linux 上是抗碎片标准手段，不要跨平台照搬。**
   - ✅ **训练中盯 `nvidia-smi`**：速度掉一个数量级、显存贴着上限、GPU 利用率还是 98% 且无 throttle——三条同时出现就是它

4. **`save_steps` 必须小于总步数。** 第一次配置写 `save_steps: 100` 而总步数只有 69 —— 等于全程不落盘，中断后 20 分钟的训练全部作废，连 `resume_from_checkpoint` 都没得续。**总步数少的小任务，save_steps 要按总步数的 1/3 设。**

5. **VLM 的 `image_max_pixels` 是训练显存的第一杠杆**，比 `cutoff_len` 影响大得多——一张图 580 个视觉 token，而指令+目标加起来才 ~170 个。

6. **注意力可视化必须用 eager**（见 §四），且 hook 里只保留"答案位置 → 图像位置"的子块，否则 `[heads, 2000, 2000]` 单层就吃几百 MB。

7. **下载踩坑**：Qwen 的 shard 1 在 ModelScope 上走到慢节点（0.6~1.4 MB/s），同一时刻 hf-mirror 实测 17 MB/s（12×）。**发现某分片掉到 1 MB/s 量级，先花 25 秒测另一个源，能省 40 分钟。** 另：`hf_hub_download` 在 hf-mirror 上用不了（huggingface_hub 1.26 会先请求 Xet 元数据，镜像不返回），退到裸 `requests` + `Range` 续传。
