## run_pipeline.sh

主控编排。仓库根目录另有一层**薄壳** `run_pipeline.sh`，作用是把工作目录固定到
仓库根（LLaMA-Factory 的 `dataset_dir` 等少数配置相对工作目录解析）。

```bash
bash run_pipeline.sh --list           # 列出各段与产物状态，不执行
bash run_pipeline.sh --quick          # 冒烟：训练 2 步 / 评测 2 题
bash run_pipeline.sh --skip-train     # 验收推荐：数据 + 评估
bash run_pipeline.sh --from train --train-stage dpo    # 失败后续跑
bash run_pipeline.sh --dry-run        # 只打印将执行的命令
```

| 参数 | 说明 |
|---|---|
| `--skip-data` / `--skip-train` / `--skip-eval` | 显式跳过某段 |
| `--with-deploy` | 额外跑部署段（**默认关**，它会留下常驻服务） |
| `--only <stage>` | 只跑一段：`data` / `train` / `eval` / `deploy` |
| `--from <stage>` | 从某段开始往后跑 |
| `--quick` | 冒烟模式，产物不可用于交付 |
| `--train-stage <s>` | 透传 step2 的 `--stage`：`sft` / `dpo` / `all` |
| `--bench` | 评测时额外跑 CEval |
| `--variant <v>` | 部署后端：`fp16` / `awq` / `gptq` / `vl`（默认 `awq`） |
| `--dry-run` / `--list` | 见上 |

**评测段的模型选择顺序**：DPO 合并产物 → SFT 合并产物 → 基座。最后这档很重要
——`--skip-train` 时训练产物不存在，退回基座才能让「数据 + 评估两段跑通」成立。
退回基座不是敷衍：它就是第 3、4 周所有对比实验的对照基线。

> ★ **透传参数一律攒进 bash 数组，不能攒进字符串。** 第一版写成
> `EVAL_ARGS="--model $EVAL_MODEL ..."`，展开时按空格分词，仓库路径里的
> `Ruibo's` 和 `Desktop/...` 被拆成两个参数，argparse 报
> `unrecognized arguments: Desktop/...`——**错误信息指向 step3_eval.py，
> 真正的错误却在主控里**。

## step1_data_prep.py

五步清洗漏斗，每步进出数量都打印并写进 `data_stats.json`。

```bash
.venv/Scripts/python.exe Week8/scripts/step1_data_prep.py
.venv/Scripts/python.exe Week8/scripts/step1_data_prep.py --quick 200   # 冒烟
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--source` | Week2 的产物 | 原始 Alpaca 池 |
| `--dpo-source` | Week4 的产物 | 偏好数据源 |
| `--out-dir` | `Week8/data` | 输出目录（同时是 LF 的 `dataset_dir`） |
| `--val-ratio` | 0.1 | 验证集比例（任务书要求 9:1） |
| `--seed` | 与 Week3/4 一致 | 划分随机种子 |
| `--tokenizer` | 基座 | 长度统计用的分词器 |
| `--max-tokens` | — | 超长样本的处理阈值 |
| `--quick N` | 0 | 只取前 N 条 |
| `--no-dpo` | — | 只处理 SFT 数据 |

**输出**：`Week8/data/{train,val}.json`、`{train,val}_sharegpt.json`、
`dpo_{train,val}.json`、`dataset_info.json`；`deliverables/data_stats.{json,md}`。

**实跑**：4975 → 清洗 4975（改动 593）→ 长度 4973 → 去重 4684（命中 289）
→ train 4216 / val 468，30.18 s。

> ★ **划分必须在这一步做完，不能交给 LF 的 `val_size`。** 两者同时存在会形成
> 二次划分：实际训练样本变成 4216 × 0.9 = 3794，eval loss 算在多切出来的 422 条上。
> 它不报错、不警告、训练照跑、曲线照出，**只是数字悄悄换了含义**。

## step2_train.sh

```bash
bash Week8/scripts/step2_train.sh                 # SFT → 合并 → DPO → 合并
bash Week8/scripts/step2_train.sh --stage sft     # 只跑 SFT(+合并)
bash Week8/scripts/step2_train.sh --dry-run       # 只打印命令
bash Week8/scripts/step2_train.sh --quick         # 冒烟（max_steps=2）
bash Week8/scripts/step2_train.sh --max-retries 5
```

**OOM 五档降配阶梯**（按对原实验的扰动从小到大）：

| 档 | 动作 | 偏离原实验？ |
|---|---|---|
| 1 | eval batch → 1 | 否，对训练数学**零影响** |
| 2 | train batch 减半 **+ accum 加倍** | 否，等效 batch 不变 |
| 3 | 同上再来一次 | 否 |
| 4 | `cutoff_len` 减半 | ★ **是** |
| 5 | `cutoff_len` 再减半 | ★ **是** |

> ★ **batch 减半与 accum 加倍永远成对出现。** 等效 batch = `batch × accum`，
> 第 3 周的冠军超参是在等效 batch=16 下调出来的。只减 batch 不补 accum，
> 每步样本少一半、梯度噪声变大、有效学习率被改，训出来的和「第 3 周的最优实验」
> 根本不是一回事，**而流水线还会若无其事地把它当成最优模型交付**。

> ★ **降 `cutoff_len` 放末档并显式标记。** 触发时日志打 ★ 警告，
> `retry_history.json` 里 `deviates_from_baseline=true`。
> 宁可交付一个「知道自己不标准」的模型，也不要交付一个「以为自己标准」的。

**两条实现约束**：① 覆盖参数必须写 `key=value` 而非 `--key value`
（LF 的 `parser.py:90-93` 走 OmegaConf dotlist）；② 不用 `set -e`，
因为脚本的核心逻辑就是「失败之后继续做事」，而 `pipefail` 是必须的
（训练要 `| tee`，没它 `$?` 拿到的是 tee 的 0）。

## step4_deploy.sh

```bash
bash Week8/scripts/step4_deploy.sh                    # awq 后端 + Gradio
bash Week8/scripts/step4_deploy.sh --variant gptq
bash Week8/scripts/step4_deploy.sh --variant vl --no-ui   # 多模态，端口自动 8001
bash Week8/scripts/step4_deploy.sh --status           # 只查健康
bash Week8/scripts/step4_deploy.sh --stop             # 停掉
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--variant` | `awq` | `fp16` / `awq` / `gptq` / `vl` |
| `--port` / `--ui-port` | 8000 / 7860 | `vl` 会自动改用 8001 |
| `--timeout` | 300 | 等 vLLM 就绪的秒数 |
| `--no-ui` | — | 不起 Gradio |
| `--status` / `--stop` / `--dry-run` | — | 见上 |

**三条踩过的坑**：

> ★ **脚本要跨 Windows / WSL 边界**——vLLM 没有 Windows 轮子只能在 WSL2，
> Gradio 在 Windows 侧。`detect_side()` 用 `uname -s` 判断，
> **不能只看 `/proc/version`——Git Bash(MSYS2) 也有这个文件**
> （内容是 `MINGW64_NT-10.0-26200 ...`），第一版据此判成 linux，
> 然后去 nohup 一个 Windows 上根本不存在的 `vllm`。

> ★ **健康检查必须打 HTTP，不能看进程在不在**——vLLM 从进程起来到能接请求要
> 40~120 秒（加载权重 + 预分配 KV cache + 捕获 CUDA graph），
> 这期间进程活着但请求全被拒。脚本轮询 `GET /v1/models` 并每 15 秒打心跳。

> ★ **curl 必须带 `--noproxy '*'`**——系统代理会把发往 `127.0.0.1` 的请求也塞进
> 代理，代理转不了 localhost，回 502。**服务是好的，请求没到。**
> 且末尾要写 `; true` 而非 `|| echo "000"`：curl 连不上时**既**输出 `000`
> **又**返回非零，后者会让函数返回 `"000000"`，所有 `= "200"` 比较静默失效。

## auto_score.py

```bash
.venv/Scripts/python.exe Week8/scripts/auto_score.py --validate          # 对 100 条人工打分回归
.venv/Scripts/python.exe Week8/scripts/auto_score.py \
    --answers Week3/deliverables/eval_answers/answers_qwen_base.json --detail
```

5 维加权（0.30 准确 / 0.25 完整 / 0.20 逻辑 / 0.15 安全 / 0.10 格式，与第 3 周人工卡一致）。

**它是什么，更重要的是它不是什么**：做的是**表面特征匹配**，是人工评分的
**代理指标**不是替代品。正当用途只有两个：**回归护栏** 和 **流水线自动化**。

**对齐质量**（对第 3 周 100 条真实人工打分回归）：模型级 Spearman **rho = 0.90**，
题级 rho = 0.699，MAE = 0.376。准确性/安全性两维题级 rho 0.877 / 0.846 最可信，
完整性只有 0.259（它数的是"要点覆盖率"，而人判完整性会考虑"对这道题什么算完整"）。

> ★ 逻辑性维度改过一次**建模方式**：第一版 `1 + 4×加权信号量` 实测均值 2.54 vs
> 人工 3.97，系统性低 1.43 分，调系数救不回来。根因是人工卡的锚点是
> 「5=完整自洽 / 3=有明显跳步 / 2=多处矛盾」——**人是默认给高分再扣的**。
> 改成「默认自洽、见到破绽才扣」后均值回到 3.9。
> **自动指标要对齐的不只是人的分数，还有人的打分结构。**

答案要点表在 `configs/eval.yaml`：把每题 `reference` 蒸馏成 `final`（决定准确性）/
`support`（决定完整性）/ `anti`（已知错答）。有些题的正确答案就写在题干里
（reason-02/04/06），这些标 `scope: conclusion` 只在结论区匹配，否则会无差别送分。

## ceval_local.py

```bash
.venv/Scripts/python.exe Week8/scripts/ceval_local.py \
    --model models/Qwen2.5-0.5B-Instruct --tag student_base
# 冒烟
.venv/Scripts/python.exe Week8/scripts/ceval_local.py --model ... --tag x \
    --limit 2 --subjects computer_network operating_system
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--model` / `--tag` | 必填 | 被评模型与标识 |
| `--n-shot` | 5 | few-shot 数（示例取自各学科 `dev` 划分，官方给的 5 条） |
| `--limit` | 0 | 每科最多评几题（0=全部，共 1346 题） |
| `--subjects` | 全部 52 | 只评部分学科 |

**口径必须跟着分数走**：本脚本用 **ppl 口径**（比 A/B/C/D 四个 token 的 logit，
每题一次前向），**不是** OpenCompass 的 `ceval_gen`（自由生成后正则抽取）。
ppl 对小模型更宽容（不惩罚"不会按格式作答"），分数系统性偏高，
**不能直接与论文里标 `ceval_gen` 的数字比较**。结果 JSON 里带 `caliber: ppl-5shot`。

**汇总用 micro 平均**（按题）而非 macro（按学科）——各科题数从 6 到 100+ 不等，
macro 会让 6 题的学科和 100 题的等权，一两道题的抖动就能挪动总分。

**正确性自检**：`_option_token_ids()` 断言 A/B/C/D 的首 token id 互不相同——
整套方法的前提就是四个选项落在四个可区分的 token 上，不成立时应当**报错**
而不是给出一个悄悄错掉的分数。

## distill_kd.py

```bash
# 冒烟：64 条样本 / 4 步 / 不保存权重
.venv/Scripts/python.exe Week8/scripts/distill_kd.py --config Week8/configs/distill_kd.yaml --smoke
# C 组（KD）
.venv/Scripts/python.exe Week8/scripts/distill_kd.py --config Week8/configs/distill_kd.yaml
# B 组（纯 SFT 对照，alpha=0，教师不加载）
.venv/Scripts/python.exe Week8/scripts/distill_kd.py --config Week8/configs/student_sft_baseline.yaml
```

损失：`L = α · T² · KL(p_teacher^(T) ‖ p_student^(T)) + (1 − α) · CE(z_s, y)`

> ★ **T² 是最容易漏的一行。** 对 `z_s` 求导，KD 梯度按 **1/T²** 缩。不乘回去的话，
> T 从 1 调到 4 会让 KD 梯度悄悄缩小约 16 倍——**α 的含义随 T 漂移**，
> α=0.5 在 T=1 和 T=4 下不是同一个权重，超参完全不可比。

> ★ **只在 assistant 回复 token 上算损失。** prompt 占 token 总数 43.5%，
> 不 mask 等于让将近一半的蒸馏信号去对齐「如何续写用户的话」这个我们不关心的任务。
> CE 和 KL 用**同一个 mask**，α 才是干净的加权。

> ★ **一份代码两组实验**：`kd_alpha=0` 时教师根本不加载，即纯 SFT 对照。
> 这保证 B/C 之间除 KD 损失项外没有任何差异（同数据、同超参、同种子、同 collator）。
> `verify_all.sh` 里有一项专门检查两份 YAML 只差 `kd_alpha`——
> 若有第二个自变量，「C − B 就是蒸馏净效果」立刻失效，整章分析作废。

**日志口径提醒**：`trainer_log.jsonl` 里的 `loss` 是**累积窗口求和**，
实测恒等于 `ce_loss × 8`（= `gradient_accumulation_steps`）。
看模型学得怎么样只能看 `ce_loss` / `ppl_train`。

## compare_distill.py

```bash
.venv/Scripts/python.exe Week8/scripts/compare_distill.py                 # 四组全跑
.venv/Scripts/python.exe Week8/scripts/compare_distill.py --skip-teacher  # 省 3B 那组
.venv/Scripts/python.exe Week8/scripts/compare_distill.py --ceval-limit 2 --skip-gen  # 冒烟
```

## build_tech_report.py

```bash
.venv/Scripts/python.exe Week8/scripts/build_tech_report.py            # 出 md + docx
.venv/Scripts/python.exe Week8/scripts/build_tech_report.py --no-docx
```

把 `reports/ch1~ch8_*.md` 拼成一份完整报告。**分章写 + 拼装脚本**把「写」和「排」
解耦：写的人只管自己那章和本章引用，编号/目录/字数/格式由脚本一次性处理，
且**可重复执行**——改完某章重跑一次即可。

四件事：

1. **文献去重重编号**——按**归一化标题**去重（取最长的点分段，去掉 markdown 强调符、
   括号补充、大小写与标点）。不能用字符串相等：各章写法不一致，
   第一版 26 条里有 5 组是同一篇的不同写法（LoRA / LlamaFactory / vLLM / C-Eval / AWQ），
   参考文献表里同一篇列两次是很显眼的硬伤。修正后 **26 → 21**。
2. **替换角标时跳过代码块**——正文的 `[1]` 是引用，但代码里的 `attn[0, head, ...]`、
   `logits[0, -1]` 形状完全一样。按 ``` 围栏切分只在非代码段替换，
   否则会把代码改坏，而且这种改坏在渲染出来的文档里极难发现。
3. **生成目录**（只到二级）。
4. **字数核对**——按中文字符数统计，**剔除**代码块、表格分隔线、图片路径。
   两种口径都打出来，避免用一个虚高的数字自欺。

**当前**：8 章 **31,666** 中文字符 / 58,575 非空白字符，13 图，21 条文献。

## verify_all.sh

```bash
bash Week8/scripts/verify_all.sh            # 快检：不占 GPU，约 1 分钟
bash Week8/scripts/verify_all.sh --full     # 全检：加 GPU 冒烟，约 10 分钟
bash Week8/scripts/verify_all.sh --list     # 只列出会检查哪些项
```

**82 项检查，每一项都真的执行**——文件存在和文件能跑是两回事。覆盖：

| 组 | 内容 |
|---|---|
| 1. 环境 | 解释器 / CUDA / llamafactory 可导入 / **五个关键包版本符合 lock** |
| 2. 脚本 | 全部 `.sh` 过 `bash -n`，全部 `.py` 过 `py_compile` |
| 3. 配置 | `pipeline.env` 能被 **dash** 加载（POSIX 兼容）/ 7 个 YAML 可解析 / **B/C 对照组有效性** |
| 4. 主控 | 全部参数组合的 dry-run + **三条反向用例**（非法参数必须失败） |
| 5. 评测 | 打分器回归 + **rho ≥ 0.85 不退化** + 后端探测 + compare 预检 |
| 6. 报告 | 三张图生成 + 八章拼装 + **字数 ≥ 6000** + **引用的图都存在** |
| 7. 交付物 | 17 个文件齐备 + JSON/CSV 可解析 + **.gitignore 未误伤验收日志** + **无权重入库** |
| 8. GPU | ceval 冒烟 / 真加载模型生成 / `--quick` 端到端（仅 `--full`） |

**两条设计**：

> ★ **分快检/全检两档**——快检必须快到你愿意每次改完代码都跑。
> 占 GPU 的检查放默认档会让人跳过它，整个自检就形同虚设。

> ★ **必须有反向用例**——只测正常路径的自检是假自检：
> 一个把所有参数都当合法的脚本同样能全绿。

自检产物写到 `Week8/logs/verify_scratch/`（靠 `WEEK8_DELIV_DIR` 环境变量），
**不碰正式交付物**。第一版没隔离，一次 `--full` 往 `eval_summary.csv` 里塞了 4 行
垃圾——自检把它本来要保护的东西弄脏了。
