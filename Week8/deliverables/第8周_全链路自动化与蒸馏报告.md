> 环境：Windows 11 + RTX 4090 (24GB) + WSL2 Ubuntu 24.04，Python 3.12.10。
> 本周把前七周的全部步骤封装成一条可一键运行的 Pipeline，并做了一次白盒知识蒸馏：
> **数据/训练自动化 → 评估/部署自动化 → 主控编排 → 知识蒸馏 → 八章技术报告 → 仓库规范化**。

## 〇、本周的四个关键判断（先说结论）

和前几周一样，动手之前先把任务书里几处会决定整周走向的地方定性。

### 1. 任务书 42.2 的「LLaMA-Factory 的蒸馏功能」在本地版本里不存在

翻本地 LF 0.9.6.dev0 @ 76a0391 的源码，三条证据：

| # | 检查 | 结果 |
|---|---|---|
| a | `grep -rniI "teacher" LLaMA-Factory/src/ --include=*.py \| wc -l` | **0** —— 没有 teacher 概念，就不可能有 teacher-student 蒸馏 |
| b | `finetuning_args.py:460` 的 stage 枚举 | `Literal["pt","sft","rm","ppo","dpo","kto"]` —— **没有 kd / distill** |
| c | 唯一的 KL 实现 `trainer_utils.py:743 _kl_divergence` | 只被 `_asft_cross_entropy` 调用。ASFT 是 DPO 家族的对齐损失，比的是 policy vs **同尺寸 reference model**，用途是防漂移，不是跨尺寸蒸馏 |

任务书原文是「利用 LLaMA-Factory 的蒸馏功能（**或自行实现**）」，所以走后一条路：
自行实现白盒 logit KD（`Week8/scripts/distill_kd.py`）。

> 这是第 **三** 次「任务书说框架支持、源码里其实没有」：第 4 周是 DPO 超参、
> 第 7 周是 `--quantization_method awq` 其实导不出 AWQ、本周是蒸馏功能。
> 得到的方法论：**任何「框架支持 X」的说法，在依赖它做决策之前先 grep 一遍源码。**

### 2. OpenCompass 这条路不通，但 CEval 这件事是能做成的

第 3 周 Day15 起 OpenCompass 就没在这台机器上装成功过，
`Week3/deliverables/OpenCompass评测分数表.md` 至今整张表都是 ⏳。
本周本想退回 LF 自带的评测器，实测发现**它也不行**——LF 上游已经把 `evaluation/`
数据加载目录整个删掉了：

```
$ git ls-files | grep '^evaluation'          # 空
$ cached_file('evaluation/ceval', 'mapping.json')
OSError: evaluation/ceval is not a local folder and is not a valid model identifier
```

但真正卡住的**不是评测方法，而是数据**——而数据是拿得到的：

```python
load_dataset('ceval/ceval-exam', name='computer_network')   # 一行就下来了
```

评测逻辑本身只有一百来行：拼 5-shot prompt、前向一次、比 A/B/C/D 四个 logit。
于是写了 `Week8/scripts/ceval_local.py`，把挂了五周的 ⏳ 变成真实分数。

> **诚实留空不等于放弃，它只是拒绝用假数字提前结账。**

### 3. 「跳过」必须是人的决定，不能是脚本的自作聪明

Pipeline 看起来更聪明的设计是「产物已存在就自动跳过」。但四段的代价差三个数量级
（32 秒 / 数小时 / 8 分钟 / 常驻），自动跳过意味着**改了配置重跑时它会悄悄用旧产物**。

这类 bug 的症状是「我明明把 lr 改了，为什么分数一模一样」——既难发现，
发现之后又会让人回头怀疑之前所有的实验结论。第 3 周做 14 组超参对比时，
只要有任何一组用了旧产物而没被发现，那一周的结论就全部作废。

所以选择**显式跳过**：`--skip-train` / `--only` / `--from` 都是人写在命令行里的决定，
脚本只负责忠实执行并在开头把计划打出来让人核对。

### 4. 部署段默认不跑

`step4` 起的是常驻服务，会一直占着显存和端口直到被显式停止。
一条「跑完就退出」的流水线突然变成「跑完还挂着两个后台进程」，
对无人值守调用（CI、夜间批处理）是灾难——下一个任务拿到的是一张已经被吃掉 20GB
的卡，而它并不知道为什么。所以 deploy 必须 `--with-deploy` 显式打开。

## 一、Day40：数据与训练自动化

### 1.1 `step1_data_prep.py` —— 五步漏斗

实跑结果（每一步的进出数量都写进 `data_stats.json`）：

```
=== SFT 清洗漏斗 ===
  0_raw            4975
  1_text_cleaned   4975   （改动 593 条：全角空格、零宽字符、重复标点）
  2_drop_empty     4975
  3_length_handled 4973   （截断 2，超长丢弃 2）
  4_deduped        4684   （SimHash 去重命中 289）
  5_train          4216      5_val  468
=== DPO 漏斗 ===
  1221 → 1219（按 prompt 去重命中 2）→ train 1097 / val 122
总耗时 30.18 s（去重 8.18 s 占大头）
```

去重用 **SimHash(64bit) + LSH(4 band × 16bit) + 汉明距离 ≤3**：

- 精确哈希只能抓完全相同的样本，而实际重复大多是「同一道题换了个提问方式」
- 两两比对是 O(n²)，4975 条要比 1237 万次，跑不完
- SimHash + LSH 分桶是 O(n)，实测 8.18 s 命中 289 条

### 1.2 ★ 划分必须在这一步做完，不能交给 LLaMA-Factory

`sft_best.yaml` / `dpo_best.yaml` 里**没有** `val_size`，验证集在 step1 就切好，
通过 `eval_dataset:` 显式传入。若同时设 `val_size`，LF 会在**已经切过的训练集上
再切一刀**形成二次划分：

- 实际训练样本变成 4216 × 0.9 = 3794 条
- eval loss 是在多切出来的 422 条上算的，而不是我们准备的那 468 条
- Week8 的 eval loss 与第 3、4 周**失去可比性**

**它不报错、不警告、训练照跑、曲线照出，只是数字悄悄换了含义。**

### 1.3 `step2_train.sh` —— OOM 五档降配阶梯

| 档 | 动作 | 是否偏离原实验 |
|---|---|---|
| 1 | eval batch → 1 | 否——对训练数学**零影响** |
| 2 | train batch 减半 **+ accum 加倍** | 否——等效 batch 不变 |
| 3 | 同上再来一次 | 否 |
| 4 | `cutoff_len` 减半 | ★ **是** |
| 5 | `cutoff_len` 再减半 | ★ **是** |

**★ 取舍一：等效 batch 必须保持不变。** 等效 batch = `batch × accum`。
第 3 周的冠军超参是在等效 batch=16 下调出来的。只减 batch 不补 accum，
等效 batch 就从 16 掉到 8：每步看到的样本少一半 → 梯度噪声变大 →
有效学习率相当于被改了 → 训出来的模型和「第 3 周的最优实验」根本不是一回事，
**而流水线还会若无其事地把它当成最优模型交付**。所以降配阶梯里两者**永远成对出现**。

**★ 取舍二：降 `cutoff_len` 放在末档，并显式标成「已偏离原实验」。**
它真的改了实验（每步 token 数减半、长样本被多截）。触发时日志打 ★ 警告，
`retry_history.json` 里 `deviates_from_baseline=true`。

> **宁可交付一个「知道自己不标准」的模型，也不要交付一个「以为自己标准」的。**

**★ 取舍三：不用 `set -e`。** 这个脚本的核心逻辑就是「命令失败之后继续做事」，
`set -e` 会在第一次训练失败时把脚本杀掉，整套重试机制永远不会被执行到。
用 `set -uo pipefail`——**`pipefail` 是必须的**：训练命令要 `| tee` 到日志，
没有它 `$?` 拿到的是 tee 的返回码（几乎永远是 0），训练崩了也会被当成成功。

**★ 取舍四：OOM 判定要「退出码非 0 **且** 日志里有显存不足特征串」。**
只看退出码不行——语法错、数据集没注册、路径写错也都是非 0，
那些重试一万次也不会好，只会把真正的错误信息埋在三层重试日志底下。

### 1.4 注入式测试：不制造真 OOM 也能验证重试逻辑

把 `$PYTHON` 换成假解释器，它打印一条真实的 `torch.OutOfMemoryError` 回溯并返回 1，
从而**确定性地**验证五档阶梯、覆盖参数、`deviates_from_baseline` 标记、JSON 写入。

实跑记录（`Week8/logs/retry_history.json`）：

| attempt | 档位 | overrides | deviates |
|---|---|---|---|
| 0 | baseline | （无） | false |
| 1 | eval batch 2→1 | `per_device_eval_batch_size=1` | false |
| 2 | ★ cutoff_len→1024 | `batch=1 accum=16 eval_batch=1 cutoff_len=1024` | **true** |
| 3 | ★ cutoff_len→512 | 同上，`cutoff_len=512` | **true** |

> 注意 attempt 2：`batch=1` 与 `accum=16` 同时出现，乘积 16 与配置文件里的等效 batch
> 相同——§1.3 取舍一要保证的性质在注入式测试里被直接验证了。

**★ 历史文件的写入不能依赖 `$PYTHON`**：`retry_history.json` 是用 sed 从 JSONL
渲染的。注入式测试会把 `$PYTHON` 换成假命令，若写入依赖那个被替换掉的解释器，
测试就测不到真实的写入路径。

## 二、Day41：评估与部署自动化

### 2.1 `step3_eval.py` —— 基准评测的四级回退

| 优先级 | 后端 | 本机实测 |
|---|---|---|
| ① | `opencompass` | ✗ 从未安装成功（第 3 周起） |
| ② | `llamafactory` | ✗ 能 import，但 `evaluation/` 数据目录被上游删了 |
| ③ | **`ceval_local`** | ✅ **本机实际生效的这一级**，自带评测器 |
| ④ | `unavailable` | 三条都不通时如实记录原因 |

每一级都把「用了哪个后端、为什么」写进 CSV 的 `bench_backend` / `bench_note` 两列。

> ★ **绝不允许出现第五种情况：跑不起来，于是填一个看起来合理的数字。**
> 一份编造的 CEval 分数比一个空格危险得多——空格会让人去查，数字不会。
> 而且它会一路污染下游：技术报告引用它、结论建立在它上面、
> 别人复现不出来时会先怀疑自己的环境。
> 同理，缺失值写 `⏳` 而**不是 `0` 或空字符串**：`0` 会被下游当成「考了 0 分」参与平均。

**解析对象是 `results.log` 文件而不是 stdout**：LF 把分数同时 print 到 stdout 和写进
文件，但 stdout 里混着 tqdm 的进度条回车，在 Windows 控制台上经常把分数行冲掉半截。

### 2.2 自动 5 维打分器：它是什么，更重要的是它不是什么

人工打分考察的是「这个回答对不对、好不好」，那需要真正读懂内容。本脚本做不到，
它做的是**表面特征匹配**。因此它是人工评分的 **proxy**，不是替代品。
正当用途只有两个：**回归护栏** 和 **流水线自动化**。

**为什么是规则法而不是 LLM-as-judge**：LLM 裁判更准，但它 ① 要占一张卡
② 不确定（同一份答卷两次跑分不同，回归护栏就废了）③ 无法解释（掉分说不出原因）。
规则法反过来：零显存、完全可复现、每一分都能追到具体哪条规则。

**对齐质量**（拿第 3 周 100 条真实人工打分做的回归）：

```
模型级 Spearman rho = 0.90（n=5，仅第 3/4 名互换）
题级 rho = 0.699，题级平均绝对偏差 MAE = 0.376
```

| 维度 | 自动 | 人工 | 差 | 题级 rho |
|---|---|---|---|---|
| 准确性 | 3.82 | 3.99 | −0.17 | **0.877** |
| 完整性 | 4.23 | 4.49 | −0.26 | 0.259 |
| 逻辑性 | 4.07 | 3.97 | +0.10 | 0.405 |
| 安全性 | 4.65 | 4.38 | +0.27 | **0.846** |
| 格式 | 4.74 | 4.56 | +0.18 | 0.537 |

**这个精度足以当回归护栏，不足以下「A 比 B 好 0.1 分」这种结论。**

### 2.3 ★ 一处建模方式的修正：逻辑性维度

第一版的逻辑性是 `1 + 4 × 加权信号量`（数连接词、数步骤号、数等式）。
实测全模型均值 **2.54**，人工是 **3.97**，系统性低了 **1.43 分**，
是五维里最大的偏差，调系数救不回来。

根因是建模方式反了：人工评分卡的锚点是「5 = 完整自洽 / 3 = 有明显跳步 / 2 = 多处矛盾」
——**人是默认给高分再扣的**；线性加分模型默认给低分再加，
于是所有语气平实、不爱用连接词的回答（尤其是代码题）都被冤枉。
改成「默认自洽、见到破绽才扣」后，均值回到 3.9 附近。

> **自动指标要对齐的不只是人的分数，还有人的打分结构。**

### 2.4 ★ `scope: conclusion` —— 一类必须单独处理的误判

有些题的正确答案**就写在题干里**：

- `reason-02`「照片里的人是我父亲的儿子」——「我父亲的儿子」是题干原话，全文匹配必然误判为答对
- `reason-04`「100 天后是星期几」——推理过程会写「1 天后是星期四，2 天后是星期五」，全文匹配会被举例骗过
- `reason-06`「5 分钟」——题干本身就写着 5 分钟

所以这些题的 `final` 标了 `scope: conclusion`，只在**结论区**匹配。
不这么做，这几题会给所有模型无差别送分，把维度分整体抬高而失去区分度。

### 2.5 `step4_deploy.sh` —— 跨 Windows / WSL 边界

**两个服务不在同一个操作系统里**：vLLM 没有 Windows 轮子，只能跑在 WSL2 的
`~/venvs/vllm`；Gradio 跑在 Windows 侧的 `.venv`。
脚本用 `uname -s` 判断自己在哪一侧，再决定是本地 `nohup` 还是
`wsl.exe -e bash -lc` 投递。

**★ 判断顺序不能反**——第一版在 Git Bash 里判成了 `linux`，然后去 nohup 一个
Windows 上根本不存在的 `vllm`。原因是 **MSYS2 也提供 `/proc/version`**：

```
$ cat /proc/version
MINGW64_NT-10.0-26200 version 3.6.9-b4195d69.x86_64 ...
```

> **「文件存在」和「文件存在且含义是我以为的那个」是两件事。**
> 跨平台脚本里的特征检测尤其容易在这里翻车，因为兼容层的存在感恰恰体现在
> 「它把你以为只有 Linux 才有的东西也提供了」。

**★ 健康检查必须打 HTTP，不能看进程在不在。** vLLM 从进程起来到能接请求要
40~120 秒（加载权重 + 预分配 KV cache + 捕获 CUDA graph）。这段时间里进程活得好好的，
但任何请求都会被拒。所以轮询 `GET /v1/models` 直到 200 或超时，
并每 15 秒打一次心跳——让人看见它在等，而不是以为脚本卡死了。

**★ `curl` 必须带 `--noproxy '*'`。** 第 7 周踩过整轮：系统代理会把发往 `127.0.0.1`
的请求也塞进代理，代理转不了 localhost，回 502。**服务是好的，请求没到。**

## 三、Day41.3：主控 `run_pipeline.sh` 与三个实跑 Bug

自动化脚本有个特点：**很多错误只在真跑的时候才出现**，dry-run、语法检查、
代码审查都发现不了。本周实跑撞到三个，各自代表一类。

### 3.1 参数攒进字符串而不是数组

```bash
EVAL_ARGS="--model $EVAL_MODEL --tag $EVAL_TAG"
run_stage eval "$PYTHON" "$SCRIPTS/step3_eval.py" $EVAL_ARGS
```

实跑立刻炸：

```
step3_eval.py: error: unrecognized arguments: Desktop/SenceTime_Weeks1-5/models/Qwen2.5-3B-Instruct
```

`$EVAL_ARGS` 展开时按空格分词，而仓库路径是 `C:/Users/Ruibo's Desktop/...`——
`Ruibo's` 和 `Desktop/...` 被拆成了两个参数。

**这个 bug 的教学价值在于报错的位置**：错误信息出自 `step3_eval.py` 的 argparse，
真正的错误却在主控脚本里。跨脚本的错误定位是最费时间的一类——
因为第一反应总是去看报错的那个文件。

### 3.2 curl 的退出码与输出同时发生

```bash
"$CURL" -s -o /dev/null -w '%{http_code}' --max-time 5 "$1" 2>/dev/null || echo "000"
```

连不上时 curl **既**把 `000` 打到 stdout（`-w` 照样输出），**又**返回非零退出码。
`|| echo "000"` 让两者都发生，函数返回 `"000000"`，
后面所有 `[ "$code" = "200" ]` 的比较全部失效。

**失效得很安静**：状态永远显示 ❌，看起来完全像「服务没起来」。

### 3.3 `detect_side()` 误判（见 §2.5）

> 这三个 bug 有个共同点：**它们都不会让脚本崩溃，只会让它给出错误的结论。**
> 崩溃是好事，错误结论才是真正的成本。

### ★ 一个意外的强证据：跨两周、跨脚本，20/20 题答案逐字节相同

这次生成的 20 条答案，与第 3 周 Day14 用 `Week3/code/eval_harness.py` 生成的
`answers_qwen_base.json` **逐题完全一致（20/20）**，五维分也分毫不差。

两次生成相隔约两周，用的是**两个独立编写的脚本**，中间还经历了一次换机重建环境

```bash

## 五、Day42：知识蒸馏

完整记录见 `Week8/docs/Day42_知识蒸馏.md`，对比表见
`Week8/deliverables/蒸馏效果对比表.md`。这里只摘要。

### 5.1 白盒 logit KD 的前提：词表完全一致（已核实）

```python
a.get_vocab() == b.get_vocab()   # True，均 151665 项
a.encode(s)   == b.encode(s)     # True
config.json 的 vocab_size        # 均 151936
```

词表对齐 ⇒ 两个模型的 logits 落在**同一个 151936 维坐标系**里，可以逐位置算 KL。
**这是能做真蒸馏的前提，也是本任务最关键的判断。**

### 5.2 ★ KL 项乘 T² —— 最容易写错的一行

对 `z_s` 求导，KD 梯度按 **1/T²** 缩。不乘回 T² 的话，把 T 从 1 调到 4
会让 KD 梯度悄悄缩小约 16 倍——**α 的含义随 T 漂移**，超参完全不可比。

### 5.3 ★ 四个对照组，而不是两组

任务书字面只需要「蒸馏前 vs 蒸馏后」两组。但 **A→C 的差值里混着两样东西**：
① 在这批数据上又训了 2 轮（纯 SFT 也能拿到）② 教师软标签带来的额外信息。
只报 A→C 就是把 ① 的功劳记在蒸馏头上。

> **C − B 才是蒸馏的净效果。**

所以加了 B 组（α=0，其余全同：同数据、同超参、同种子、同 collator），
再加教师 D 作为天花板参照。一份代码两组实验（靠 `kd_alpha` 切换），
保证 B/C 之间除 KD 损失项外没有任何差异。

### 5.4 训练记录

| 项 | B · 纯 SFT（α=0） | C · KD（α=0.5, T=2） |
|---|---|---|
| 样本 / 优化步 | 4649 / 582 | 同左 |
| 参与损失的 assistant token | 637,245（**56.5%**） | 同左 |
| CE 首→末 | 1.8402 → **1.2925** | 1.8408 → **1.4044** |
| 训练集 PPL 首→末 | 6.298 → **3.642** | 6.301 → **4.073** |
| KD 项首→末 | —（恒为 0） | 2.1802 → **1.2187**（降 44%） |
| 峰值显存（整卡） | 21,532 MiB | 24,117 MiB |

C 组的 CE 高于 B 组是**预期之中**的：α=0.5 意味着只有一半的损失权重放在硬标签上。
**CE 更高本身不是坏消息**——要问的是这半份权重换来的东西值不值（见 §5.6）。

KD 项从 2.18 降到 1.22（**降 44%**）是「蒸馏确实在工作」的直接证据——
学生的输出分布真的在向教师靠拢，而不是 KD 项挂在那里不动。

### 5.5 ★ 一次被 GPU 争用暴露的性能悬崖：38.5 s/it → 2.2 s/it

C 组第一次启动时（另有一个游戏占约 10GB 显存），速度是 **38.5 s/it**；
关掉之后重跑，稳定在 **2.2 s/it**——**17 倍**。

B 组峰值 21.5GB 刚好塞得下，C 组要多加一个 6.2GB 的教师 → 显存溢出 →
**Windows 的 sysmem fallback**：驱动不报 OOM，改用系统内存兜底，训练**静默降速**。

危险之处在于**它不报错**——如果没有 B 组 2.4 s/it 作为对照，
38.5 s/it 很容易被当成「KD 本来就慢」而接受，然后得出
「蒸馏代价太高、不实用」的错误结论。

> **跨实验比较性能之前，先确认两次测量的外部条件相同。**
> 这和第 7 周「用 nvidia-smi 量不出量化省了多少显存」是同一类错误的两个面：
> 一个是口径不对，一个是条件不同。
>
> 同样地，上表里 B 组 23.63 min / C 组 21.62 min **不能拿来比较**——
> B 是在游戏运行期间跑的。放在文档里是为了留下记录，不是为了下结论。

### 5.6 效果对比

见 `Week8/deliverables/蒸馏效果对比表.md`（`compare_distill.py` 自动生成，全部实测）。
三个指标缺一不可：**只看 CEval 会漏掉「更快」，只看速度会漏掉「更笨」。**

### 6.1 ★ 替换角标时必须跳过代码块

正文里的 `[1]` 是引用，但代码块里的 `attn[0, head, ...]`、`plt.subplots()[1]`
形状完全一样。脚本按 ``` 围栏切分，**只在非代码段做替换**——
否则会把代码改坏，而且这种改坏在渲染出来的文档里极难发现。

### 6.2 ★ 文献去重不能用字符串相等

各章由不同人/不同时间写成，同一篇论文的写法并不一致：

```

ch5  "Hu E., et al. *LoRA: Low-Rank Adaptation of Large Language Models*. ICLR 2022."
```

字符串比对下这是两条。第一版就是这样，**26 条文献里有 5 组是同一篇的不同写法**
（LoRA / LlamaFactory / vLLM / C-Eval / AWQ），参考文献表里同一篇列两次，是很显眼的硬伤。

改成按**归一化后的标题**去重（取最长的点分段，去掉 markdown 强调符、括号补充、
大小写和所有标点）之后，26 → **21 条**。作者列表的写法差异正好被排除在键之外——

## 七、自动化逼出来的三个「本该早就想清楚」的问题

本周产出的不是模型而是流程。流程本身的价值，除了省人力，
更在于**它逼你把每一个隐式决定显式化**。手工跑的时候「这次 batch 调小了一点」
「这次验证集是临时切的」都能靠记忆糊过去；写进脚本时，这些地方都会变成必须回答的问题。

具体是这三个：

1. **验证集到底是谁切的**（§1.2）—— `val_size` 与显式 `eval_dataset` 同时存在会形成
   二次划分。手工跑时被「反正每次都这么跑」糊过去了，写进流水线时必须二选一，
   才发现原来一直有两个验证集。
2. **OOM 降配时等效 batch 变了没有**（§1.3）—— 手工遇到 OOM 的自然反应是
   「把 batch 调小」，不补 accumulation 的话训出来的就是另一个实验。
3. **跑不起来的评测该记什么**（§2.1）—— 手工阶段这件事可以一直挂着（挂了五周）。
   写进流水线时必须回答：那一格填什么？答案是多级回退 + 如实记录，
   而不是填一个看起来合理的数字。

> **这三个问题的答案，比 Pipeline 本身更有价值。**
